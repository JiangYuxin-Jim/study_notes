# hello-agents 8.3.5 · 高级检索策略：多查询扩展（MQE）与假设文档嵌入（HyDE）

> 所属：hello-agents 第八章「记忆与检索」8.3.5 节延伸学习
> 学习日期：2026-10-25
> 一句话：**RAG 的效果上限不取决于生成，而取决于检索捞回来的东西对不对**。MQE 和 HyDE 都是在"捞之前先把问题加工一下"。

---

## 一、为什么需要它们：查询-文档的"表述鸿沟"

RAG 的基本动作是 "把 query 向量化 → 在向量库里找最近的 chunk"。问题在于：

- **词汇不匹配（vocabulary mismatch）**：用户问"怎么快速上手 Python"，文档里写的是"初学者入门教程/学习路径"。**语义相同，用词不同**，向量也不够近，捞不到。
- **疑问句 vs 陈述句的语义落差**：query 是疑问句（"什么是 MQE？"），文档是陈述句（"MQE 是一种通过生成多样化查询……的技术"）。两者在向量空间里天然有一段距离——**问题在找答案，但问题和答案长得不像**。
- **单一表述 = 单一视角**：一次检索只能命中 query 那一个"切面"的相关文档，别的切面全漏。

这两个坑对应的正是两条技术路线：

| 问题 | 技术 | 直觉 |
|------|------|------|
| 用词多样 → 只查一种说法会漏 | **MQE** 多查询扩展 | 一句话换几种说法，多问几遍 |
| 问句和答句不像 → 向量距离大 | **HyDE** 假设文档嵌入 | 先瞎编一个答案，拿答案去找答案 |

## 二、多查询扩展（Multi-Query Expansion, MQE）

### 2.1 核心思想

**同一个问题有多种表述方式，不同表述能匹配到不同文档。** 让 LLM 把一句 query 改写成 N 个语义等价或互补的变体，分别检索，再合并结果。

例：

```
原始：如何学习 Python
扩展：Python 入门教程 / Python 学习方法 / Python 编程指南
```

### 2.2 实现要点（HelloAgents `_prompt_mqe`）

```python
def _prompt_mqe(query: str, n: int) -> List[str]:
    llm = HelloAgentsLLM()
    prompt = [
        {"role": "system", "content": "你是检索查询扩展助手。生成语义等价或互补的多样化查询。使用中文，简短，避免标点。"},
        {"role": "user", "content": f"原始查询：{query}\n请给出{n}个不同表述的查询，每行一个。"}
    ]
    text = llm.invoke(prompt)
    lines = [ln.strip("- \t") for ln in (text or "").splitlines()]
    outs = [ln for ln in lines if ln]
    return outs[:n] or [query]   # ← 关键：失败必须回退成原 query
```

几个工程细节值得抄走：

1. **system 里写死约束**："语义等价或互补""简短""避免标点"——输出是要直接喂 embedding 的，标点和寒暄会污染向量。
2. **每行一个**：用换行做结构化解析，比要求模型输出 JSON 更抗格式漂移。
3. **`[:n]` 硬截断 + `or [query]` 兜底**：LLM 有时会返回 5 条、有时会返回带解释的一段话。截断保证数量上限，兜底保证**扩展失败时系统退化为普通检索而不是检索为空**。
4. **`except Exception: return [query]`**：检索增强是"锦上添花"，不能因为 LLM 挂了导致主流程 500。

### 2.3 收益与代价

- ✅ **提升召回率（recall）**：官方口径提升 30%–50%。对模糊查询、口语化查询、专业术语查询效果最明显。
- ✅ 天然并行：N 个查询互不依赖，可以并发检索。
- ❌ **额外一次 LLM 调用**（延迟 + 成本），扩展查询越多，向量检索次数是线性增长的。
- ❌ 可能引入**噪声扩展**：改写跑偏时会捞回不相关的文档，把 top-k 挤占掉。
- ❌ 不解决"问句 vs 答句"的语义落差——它改的是**表述**，不是**文体**。

## 三、假设文档嵌入（Hypothetical Document Embeddings, HyDE）

### 3.1 核心思想：**用答案找答案**

```
传统检索：  问题  ----向量相似度---->  文档
HyDE：      问题 → LLM 生成"假设答案" ----向量相似度---->  真实文档
```

先让 LLM 针对问题**直接写一段似是而非的答案段落**（可能内容有错、可能有幻觉，无所谓），把这个**假设答案**向量化后去检索真实文档。

为什么有效？

- 假设答案与真实答案**同在"陈述句 + 领域术语"的语义空间**，距离远小于问题与答案的距离。
- 即使假设答案事实错了，它包含的**关键术语、概念、表述风格**是对的，足以把检索器引导到正确的文档区域。
- 本质是一种**查询改写（query rewriting）**，但改写的目标是"变成文档的样子"，而不是"变成另一种问法"。

### 3.2 实现要点（HelloAgents `_prompt_hyde`）

```python
def _prompt_hyde(query: str) -> Optional[str]:
    llm = HelloAgentsLLM()
    prompt = [
        {"role": "system", "content": "根据用户问题，先写一段可能的答案性段落，用于向量检索的查询文档（不要分析过程）。"},
        {"role": "user", "content": f"问题：{query}\n请直接写一段中等长度、客观、包含关键术语的段落。"}
    ]
    return llm.invoke(prompt)
```

细节同样讲究：

- **"不要分析过程"**：否则模型先输出"让我分析一下这个问题其实是在问……"，这段元话语会被向量化，把检索带偏。
- **"中等长度"**：太短则术语覆盖不足（退化成普通 query），太长则主题被稀释、且浪费一次 embedding。
- **"客观、包含关键术语"**：让输出贴近**文档文体**，而不是贴近**对话文体**。
- 失败返回 `None`，调用方 `if hyde_text:` 跳过——**HyDE 是可选的加分项，不是必经步骤**。

### 3.3 收益与代价

- ✅ **提升精度（precision）**，尤其**专业领域**查询：术语密度上来了，能打到领域内的正确段落。
- ✅ 天然桥接"问句-答句"鸿沟。
- ❌ **幻觉风险**：假设答案可能朝错误方向引导（错得很自信时最麻烦）。降幻觉的办法是**只当检索用，题目答案必须来自真实 chunk**。
- ❌ **额外一次 LLM 调用 + 一次 embedding**，延迟明显（比 MQE 更贵：MQE 的扩展短，HyDE 要生成长段落）。
- ❌ 简单事实型查询收益有限、甚至掉点（本可以直接匹配）。

## 四、统一扩展检索框架：扩展 → 检索 → 合并

HelloAgents 把两者塞进同一个函数 `search_vectors_expanded()`，用开关控制：

```python
search_vectors_expanded(
    query=query, top_k=8,
    enable_mqe=True, mqe_expansions=2,
    enable_hyde=True,
    candidate_pool_multiplier=4,
)
```

### 4.1 三步流水线

```
1. 扩展 (Expand)   原始 query + MQE 的 n 个变体 + HyDE 的假设段落  → expansions[]
2. 检索 (Retrieve) 每个 expansion 各自 embed + 向量检索 → 各自候选
3. 合并 (Merge)    按 memory_id 去重（保留最高分）→ 全局按 score 降序 → 取 top_k
```

### 4.2 三个设计上的巧思

**① 候选池放大（`candidate_pool_multiplier = 4`）**

```python
pool = max(top_k * candidate_pool_multiplier, 20)   # 8 × 4 = 32
per  = max(1, pool // max(1, len(expansions)))      # 32 / 4 = 8 each
```

为什么不能每个 expansion 只取 top_k？因为**合并会去重**——多路结果重叠时，去重后总数会缩水。先给每路分一个更大的配额（总池 = top_k 的 4 倍），合并去重后才够填满 top_k。这是"**宁可多捞再排掉，不要捞不够**"的工程取舍。

**② 去重时保留最高分**

```python
if mid not in agg or s > float(agg[mid].get("score", 0.0)):
    agg[mid] = h
```

同一个 chunk 可能被多个 expansion 命中（说明它**多角度都相关**，信号很强）。去重时保留最高分而不是累加，是为了避免"被多次命中"无限压过真正高相关的单次命中——**分数可比性**优先。

**③ 扩展列表先去重再切分**

```python
uniq = []; 
for e in expansions:
    if e and e not in uniq: uniq.append(e)
```

避免 MQE 生成和原 query 完全一样的句子（重复消耗一次检索配额）。

### 4.3 还有一层过滤：RAG 数据隔离

```python
where = {"memory_type": "rag_chunk"}
if only_rag_data:
    where["is_rag_data"] = True
    where["data_source"] = "rag_pipeline"
if rag_namespace:
    where["rag_namespace"] = rag_namespace
```

这和第八章"记忆 + RAG 同住一个向量库"直接相关：**记忆条目和文档 chunk 混在同一个 Qdrant 集合里**，必须靠 metadata 过滤把它们隔开，否则"检索文档"会捞出一堆用户对话记忆。`rag_namespace` 还能做多知识库隔离。

## 五、怎么选：策略组合建议

| 场景 | 建议 | 理由 |
|------|------|------|
| **一般查询** | 启用 MQE | 性价比最高，只多一次轻量 LLM 调用，主要治"用词不匹配" |
| **专业领域查询**（论文/法律/医疗/代码） | **MQE + HyDE 同开** | MQE 拓展广度，HyDE 补足术语密度，互补 |
| **性能敏感**（低延迟/高并发） | 基础检索，或仅 MQE | HyDE 生成长段落太贵 |
| **简单事实型**（"某某的生日"） | 基础检索 | 改写收益低，还可能带偏 |
| **兜底原则** | 所有扩展失败 → 退化为基础检索 | 增强手段不能成为单点故障 |

**一句话记忆法**：MQE 治「**怎么说**」，HyDE 治「**长什么样**」，统一框架负责「**不重复、不漏、不失序**」。

## 六、本章进阶检索 vs 其它 RAG 技术的定位

| 技术 | 干预位置 | 治什么 | 与本文关系 |
|------|----------|--------|-----------|
| **MQE** | 检索前·查询侧 | 词汇不匹配 → 召回率 | 本文 |
| **HyDE** | 检索前·查询侧 | 问句/答句语义鸿沟 → 精度 | 本文 |
| 混合检索（BM25 + 向量） | 检索中·多路召回 | 精确词匹配 + 语义匹配 | all-in-rag ch4，与 MQE 同属"多路召回"思路 |
| 重排序 Rerank | 检索后·精排 | 粗排噪声 → 精度 | 与本文正交，可叠加 |
| 查询分解 / Text2SQL | 检索前 | 复杂多跳问题 | all-in-rag ch4 |
| 知识图谱 RAG | 索引侧 | 结构化关系推理 | all-in-rag ch7 |

**共同规律**：RAG 的优化点**大量集中在"检索前"和"检索后"**，中间的向量相似度计算反而很少动。这也解释了为什么"换个更好的 embedding 模型"往往不如"把 query 改写一下"见效快。

## 七、代码上可复用的小模式（本篇真正的干货）

1. **增强功能一律 try/except 回退到原 query**——别让 LLM 抽风打挂检索链路。
2. **LLM 输出用换行分割 + strip 掉 `-` 和空格**，比要 JSON 稳。
3. **硬限制数量** `[:n]`，防止模型"多说两句"。
4. **候选池倍率**（4x）是复用性极强的参数：任何"多路召回后合并去重"的场景都适用。
5. **改写 prompt 里显式禁止"分析过程"和"标点"**——因为输出向量化的是字面内容，元话语即噪声。
6. **metadata 过滤优先于向量过滤**：多数据源同库时，靠 `where` 而非靠"分数高"来隔离。
