# 第九章 上下文工程（Context Engineering）

> 学习日期：2026-10-19
> 课程：hello-agents / 第九章「上下文工程」
> 核心主题：从「写对提示词」升级到「管好整个上下文窗口」。上下文是**有限资源、边际收益递减**的资源，本章先讲清「有效上下文的解剖学」（系统提示 / 工具 / 示例）与三种长时程手段（压缩整合 / 结构化笔记 / 子代理），再把第八章的记忆与 RAG 接到第九章的 **ContextBuilder（GSSC 流水线）** 上——记忆和 RAG 提供"候选信息"，ContextBuilder 负责"选出并组织成最优上下文"。
> 配套回顾：第七章自建框架（万物皆为工具）· 第八章记忆与检索（MemoryTool / RAGTool）

## 9.1 什么是上下文工程

**上下文** = 对 LLM 采样时包含的那一组 tokens。工程问题就是：在模型固有约束下，**优化这些 tokens 的效用**，稳定拿到期望行为。

> 心智模型：每次调用前都问一遍——**模型此刻看到的整体状态是什么？这种状态最可能诱发什么行为？** 这就是"在上下文中思考"。

### 9.1.1 上下文工程 vs 提示工程

| 维度 | 提示工程（Prompt Engineering） | 上下文工程（Context Engineering） |
|------|------------------------------|--------------------------------|
| 关注点 | 怎么写提示词（措辞、结构、系统提示写法） | 推理阶段**策划与维护最优 token 集合** |
| 范围 | 主要是系统提示/单轮指令 | 系统指令 + 工具 + MCP + 外部数据 + 消息历史 + 记忆检索结果 |
| 时间尺度 | 单轮、精调式优化 | 跨多轮、长时程运行的持续治理 |
| 关系 | — | **提示工程的自然演进**（子集），不是替代 |

循环运行的智能体会不断产出"下一轮可能相关"的数据，这些必须被**周期性提炼**。所以上下文工程的手艺在于：从持续膨胀的"候选信息宇宙"里，**甄别哪些该进入有限的窗口**。

## 9.2 为什么上下文工程重要

### 9.2.1 上下文腐蚀（Context Rot）

针堆找针（needle-in-a-haystack）类基准揭示：**上下文窗口里的 token 越多，模型准确回忆信息的能力反而下降**。几乎所有模型都有这个特征（只是退化曲线平滑度不同）。

原因在架构与训练分布：

- Transformer 让每个 token 与所有 token 建立关联，理论上是 **n² 级两两注意力**；上下文变长后这些关系被"拉薄"，注意力被稀释。
- 训练数据里**短序列远多于长序列**，模型对"全上下文依赖"的经验和专门参数都更少。
- 位置编码插值能让推理时"适配"更长序列，但会牺牲对 token 位置的精确理解。

结论：上下文是**有限资源、边际收益递减**，就像人有有限的工作记忆，LLM 也有一笔**注意力预算**。而且它是"性能梯度"而非"悬崖"——长上下文下依然能用，但检索精度和长程推理都变差。

> 💡 好的上下文工程目标：**用尽可能少、但高信号密度的 tokens，最大化拿到期望结果的概率。**

### 9.2.2 有效上下文的「解剖学」

**① 系统提示（System Prompt）**

- 语言清晰直白，信息层级"刚刚好"。
- 两极误区：
  - **过度硬编码**：把复杂脆弱的 if-else 逻辑写进提示，长期维护成本高、易碎。
  - **过于空泛**：只给宏观目标和泛化指引，缺**具体信号**，或假定了错误的"共享上下文"。
- 建议**分区组织**：`<background_information>`、`<instructions>`、工具指引、输出描述等，用 XML/Markdown 分隔。
- 追求 **"最小必要信息集"**（注意：最小 ≠ 最短）。方法：先用最好的模型在**最小提示**上跑，再按失败模式增补清晰指令与示例。

**② 工具（Tools）**

工具定义了智能体与信息/行动空间的**契约**，必须促进效率（返回 token 友好的信息 + 鼓励高效行为）：

- 职责单一、相互低重叠、接口语义清晰；
- 对错误鲁棒；
- 入参描述明确无歧义。
- 典型失败模式是**臃肿工具集**：边界模糊，连"选哪个工具"都含混。<br>👉 **如果人类工程师都说不准用哪个工具，别指望智能体能做好**（呼应 LangChain 笔记里的 **MVTS 最小可行工具集**）。

**③ 示例（Few-shot）**

始终推荐提供，但不要罗列所有边界条件。精挑**多样且典型**的示例直接"画像"期望行为——**好的示例胜过千言万语**。

> 总纲：**信息充分但紧致**。

### 9.2.3 上下文检索：从预检索到 JIT

一个简洁定义：**智能体 = 在循环中自主调用工具的 LLM**。

工程实践正从"推理前一次性 embedding 检索"过渡到 **及时上下文（Just-in-time, JIT）**：

- 不预加载所有相关数据，而是维护**轻量引用**（文件路径、存储查询、URL）；
- 运行时通过工具动态加载，用 `head` / `tail` 之类命令分析大体量数据，**不把整块塞进上下文**；
- 认知模式像人：我们不死记全部信息，而是用文件系统、收件箱、书签等外部索引按需提取。
- **引用的元数据本身也在传递语义**：目录层级、命名约定、时间戳都隐含"目的与时效"——`tests/test_utils.py` 和 `src/core/test_utils.py` 的暗示完全不同。
- 由此实现**渐进式披露（Progressive Disclosure）**：每一步交互产生新上下文，反过来指导下一步；文件大小暗示复杂度、命名暗示用途、时间戳暗示相关性。智能体按层建立理解，只在工作记忆里保留"当前必要子集"，用"记笔记"补充持久化，避免被"大而全"拖垮。

代价与权衡：运行时探索比预计算检索**更慢**，且需要"有主见"的工程设计（正确的工具 + 启发式），否则智能体会误用工具、追死胡同、浪费上下文。

> ⭐ 常见最优解是**混合策略**：前置加载少量"高价值"上下文保速度（如 README/项目约定），同时提供 `glob`、`grep` 等原语让智能体按需自主探索——绕开过时索引和复杂语法树的沉没成本。

### 9.2.4 面向长时程任务的三种工程手段 ⭐

长时程任务（大型代码库迁移、数小时系统研究）要在超出窗口的序列中保持连贯、一致、目标导向。**单纯加大窗口治不了"上下文污染"与相关性退化**，需要三种手段：

#### ① 压缩整合（Compaction）

- **定义**：接近窗口上限时做高保真总结，用摘要**重启一个新窗口**。
- **保留什么**：架构性决策、未解决缺陷、实现细节；**丢弃**重复的工具输出与噪声。新窗口 = 压缩摘要 + 最近少量高相关工件（如"最近访问的若干文件"）。
- **调参顺序**：先优化**召回**（别漏关键信息），再优化**精度**（剔冗余）。最安全的"轻触式"压缩是先清理**深历史里的工具调用与结果**。

#### ② 结构化笔记（Structured Note-taking / Agentic Memory）

- **定义**：以固定频率把关键信息写进**上下文之外**的持久化存储，后续按需拉回。
- **价值**：极低的上下文开销维持持久状态与依赖关系。典型：TODO 列表、项目 NOTES.md、关键结论/依赖/阻塞项索引——跨几十次工具调用、多轮上下文重置仍能保持进度一致。
- **不限于编码**：长期策略任务、游戏/仿真里的目标管理与计数同样适用。配合第八章 `MemoryTool` 可直接实现文件式/向量式外部记忆。

#### ③ 子代理架构（Sub-agent Architecture）

- **思想**：主代理负责高层规划与综合；多个专长子代理在**干净的上下文窗口**里各自深挖、调工具、探索，只回传**凝练摘要**（常见 1000–2000 tokens）。
- **价值**：关注点分离。庞杂的搜索上下文留在子代理内部，主代理专注整合推理；适合需要并行探索的复杂研究任务。（公开的多智能体研究系统显示，该模式在复杂研究任务上显著优于单代理基线。）

#### 选型经验法则

| 手段 | 适用场景 | 关键词 |
|------|---------|--------|
| 压缩整合 | 需要长对话连续性 | **接力** |
| 结构化笔记 | 有里程碑/阶段性成果的迭代开发与研究 | **外存** |
| 子代理架构 | 复杂研究与分析、可并行探索 | **分工** |

## 9.3 在 Hello-Agents 里的落地：ContextBuilder

### 9.3.1 设计动机

第八章给了两个"信息源工具"（MemoryTool 检索记忆、RAGTool 检索知识库），但**谁来把这些碎片拼成一份能给 LLM 的上下文？** 答案就是 ContextBuilder——把散乱候选变成**预算内、结构化、相关性最高**的上下文。

### 9.3.2 核心数据结构：ContextPacket

一切候选信息统一封装成 **ContextPacket**（信息包）：

- `content`：文本内容
- `timestamp`：时间戳（用于计算新近性）
- `token_count`：token 数（用于预算控制）
- `relevance_score`：相关性分数（0–1）
- `metadata`：类型标签（`system_instruction` / `rag_result` / `conversation_history` / `memory` …）与优先级

> 设计味道：**统一的中间表示**。不管信息来自系统指令、记忆、RAG 还是对话历史，先归一成 Packet，后面三个阶段（选择/组织/压缩）才能统一处理——和第七章"万物皆为工具"的思路一致。

### 9.3.3 GSSC 流水线详解 ⭐（本章核心）

**Gather → Select → Structure → Compress**

#### （1）Gather：多源信息汇集

从多个来源汇集候选包，关键在**容错性 + 灵活性**：

1. **系统指令**：最高优先级，`relevance_score=1.0` 固定，**不参与评分**；
2. **记忆检索**：`memory_tool.run({"action":"search","query":user_query,"limit":10,"min_importance":0.3})`；
3. **RAG 检索**：`rag_tool.run({"action":"search","query":user_query,"limit":5,"min_score":0.3})`；
4. **对话历史**：**只保留最近 5 条**（`history[-5:]`），基础相关性 0.6；
5. **自定义信息包**：外部显式注入。

三个设计考虑：
- 每个外部源都 **try-except 包裹** → 单源失败不影响整体；
- 系统指令标高优先级 → 永远保留；
- 历史限量 → 别让历史吃光窗口。

#### （2）Select：智能信息选择（决定质量的关键）

1. **分离系统指令**，先扣掉它占的 token，得到 `remaining_tokens`（若 ≤0，只返回系统指令并告警）；
2. 对其它包计算两个分：
   - **相关性** `relevance_score`：默认值 0.5 的才重算。示例用 **Jaccard 相似度**（分词后交集/并集）——简单但可替换，生产环境换成向量相似度。
   - **新近性** `recency`：**指数衰减** `exp(-0.1 × age_hours / 24)`，24h 内保持高分，之后递减，夹在 `[0.1, 1.0]`。
3. **综合分** = `relevance_weight × 相关性 + recency_weight × 新近性`（权重可配）；
4. **过滤**：相关性 < `min_relevance` 的直接丢；
5. **排序 + 贪心填充**：按综合分降序，能塞进预算就塞，塞不下就 `break`。

> 💡 三点工程味：①**评分可配置**（相关 vs 新近的权重就是产品性格）；②**贪心而非最优**（背包问题是 NP 的，贪心足够且可解释）；③**先扣系统指令再分配**，保证关键信息不被挤掉。

#### （3）Structure：结构化输出

按类型分组，套进固定分区模板：

```text
[Role & Policies]   ← system_instruction
[Task]              ← user_query
[Evidence]          ← rag_result / knowledge（多篇用 --- 分隔）
[Context]           ← 记忆 / 历史 等其它
[Output]            ← 输出要求（"基于以上信息，提供准确、有据的回答"）
```

好处：**可读性**（人和模型都容易理解结构）、**可调试性**（哪块出问题一眼看出）、**可扩展性**（新增信息源只需新增分区）。

> 呼应 9.2.2 的系统提示分区建议：结构不是格式化强迫症，而是**让注意力分配变得可控**。

#### （4）Compress：兜底压缩

- 先 `_count_tokens`，没超就原样返回（**压缩是兜底，不是常规路径**）；
- 超了就**按分区切分**（`split("\n\n")`）逐段保留：能完整保留就保留，剩余空间不足则**部分截断**（至少留 50 tokens）并标注 `[... 内容已压缩 ...]`，然后 break；
- 截断用字符/token 比例估算；token 计数是简化版（中文 1 字 ≈ 1 token、英文 1 词 ≈ 1.3 token，生产环境用真 tokenizer / LLM 摘要替换）。

> 原则：**保持结构完整性**——哪怕预算紧张，也尽量每块都留点关键信息，而不是把某一块整个砍掉。

### 9.3.4 三个阶段的对照（记忆版）

| 阶段 | 输入 | 核心操作 | 失败的后果 |
|------|------|---------|-----------|
| Gather | 查询 / 历史 / 指令 / 自定义包 | 多源检索 + try-except 容错 | 少信息（漏召回） |
| Select | 候选包 + token 预算 | 相关+新近加权评分 → 过滤 → 贪心填充 | 上下文被噪声淹没 |
| Structure | 选中的包 | 按类型分到 Role/Task/Evidence/Context/Output | 模型分不清哪是证据哪是要求 |
| Compress | 超限上下文 | 分区截断 + 标注 | 结构崩塌 / 关键信息丢失 |

## 9.4 NoteTool：结构化笔记（Agentic Memory 落地）

对应 9.2.4 的第二种手段：**把关键信息写到上下文之外**，需要时再拉回来。

- **设计理念**：智能体的"外置笔记本"。以结构化格式（多条笔记：标题/内容/标签/时间/分类）持久化到文件，支持**写、读、搜、列、更新、删**等操作。
- **与 ContextBuilder 深度集成**：Gather 阶段可以把 NoteTool 的相关笔记作为候选包汇入；长任务中用它维护 TODO、进度、关键结论、依赖与阻塞项。
- **为什么有效**：笔记占用的不是上下文窗口，而是**磁盘**；需要时才把"当前必要子集"检索回来——正是 9.2.3 的**渐进式披露 + JIT 上下文**。

> 🔗 对照 learn Claude Code：`CLAUDE.md` / TodoWrite / NOTES 式外存，本质都是结构化笔记；差值只是"谁触发写入、写在哪"。

## 9.5 TerminalTool：即时文件系统访问

对应 JIT 与渐进式披露的"工具侧"：让智能体**直接操作文件系统**（ls / cat / head / tail / grep / 写入等），自己去探索数据，而不是被喂一整块。

- **安全机制**：工作目录沙箱限制（只能在允许的根目录内操作）、危险命令拦截/白名单、超时与输出长度限制。
- **典型用法**：先 `ls` 看结构 → 按命名/大小/时间挑文件 → `head`/`grep` 局部读取 → 只把相关片段带进上下文。
- **价值**：把"上下文预算"从"预加载"转为"按需付费"，同时用文件元数据（路径/命名/时间）引导决策。

## 9.6 本章总结

1. **范式升级**：提示工程 → 上下文工程。前者写提示，后者管理**整个 token 状态**（指令/工具/外部数据/记忆/历史）。
2. **为什么重要**：上下文腐蚀 + n² 注意力稀释 + 训练分布偏短序列 ⇒ 上下文是有限资源，有"注意力预算"，边际收益递减。
3. **上下文解剖学**：系统提示（分区、最小必要信息集，忌硬编码与空泛）· 工具（单一职责、MVTS、别臃肿）· 示例（多样典型，胜过千言万语）。总纲：**信息充分但紧致**。
4. **检索范式**：预检索 → **JIT 及时上下文**（轻量引用 + 运行时按需加载 + 元数据隐含语义 + 渐进式披露），落地常见"前置高价值 + 工具自主探索"的混合策略。
5. **长时程三件套**：压缩整合（接力）、结构化笔记（外存）、子代理架构（分工）。
6. **工程落地 GSSC**：Gather（多源容错汇集）→ Select（相关性×新近性 + 阈值过滤 + 贪心填充）→ Structure（Role/Task/Evidence/Context/Output 分区）→ Compress（分区截断兜底）。
7. **配套工具**：NoteTool（结构化笔记外存）、TerminalTool（文件系统 JIT 访问 + 沙箱安全）。
8. **串联全章**：第八章的记忆与 RAG 是**信息源**，第九章的 ContextBuilder 是**调度与装配者**，两者合成"LLM 到底看到什么"的完整链路。

### 🔗 与下一步衔接

- 第十章「智能体通信协议」：MCP（模型↔工具）/ A2A（代理↔代理）/ ANP（去中心化网络）+ 自建 MCP Server——解决"上下文之外怎么接世界、怎么找同伴"。
- 与 LangChain 对照：ContextBuilder ≈ LangChain 的 `Summarization`/`ContextEditing` 中间件 + Prompt 模板 + state reducer 的组合；Middleware 的"压缩、动态工具、动态 prompt"其实就是上下文工程的**框架化封装**。

## 习题自检

1. 上下文工程与提示工程的分界线在哪里？为什么说前者是后者的"自然演进"而非替代？
2. 什么是上下文腐蚀？从注意力机制与训练数据分布两个角度解释它为何必然存在。
3. 为什么说"最小"不等于"最短"？"先用最小提示试跑再按失败模式增补"的好处是什么？
4. JIT 上下文与预检索各有什么代价？什么情况下该用混合策略？
5. 压缩整合 / 结构化笔记 / 子代理架构分别对应哪类任务？分别的关键词是什么？
6. GSSC 四个阶段各自解决什么问题？为什么 Select 用贪心而不是最优解？
7. 为什么 ContextBuilder 里系统指令不参与评分、且要先扣掉它的 token？
8. 新近性为什么用指数衰减？夹在 `[0.1, 1.0]` 而不是 `[0, 1]` 有什么用意？（提示：老信息也不该被彻底归零）
