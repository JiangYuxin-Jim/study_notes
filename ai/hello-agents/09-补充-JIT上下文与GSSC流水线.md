## 一、为什么需要 JIT：从「预检索」到「按需取用」

### 1.1 预检索（Pre-retrieval）的老路

传统 RAG 的做法是**推理前一次性检索**：用户提问 → embedding 检索 Top-K → 塞进 prompt → 一次性生成。

问题在于：**你并不知道模型到底需要什么，就得先赌一把**。

- 赌错了 → 噪音占预算，真正的关键信息没进窗口；
- 赌对了也只能用一次 → 多轮对话里，每一轮都要重新赌；
- 数据量一大 → 只能"预先切片"，切分粒度一旦定死，后面想换视角就难。

### 1.2 JIT（Just-in-Time）上下文的核心思想

> **不要预先把数据搬进上下文，而是把「怎么拿到数据」的轻量引用放进上下文。**

| 维度 | 预检索（Pre-retrieval） | JIT 及时上下文 |
|------|------------------------|----------------|
| 何时取数 | 推理**前**一次性 | 推理**过程中**按需 |
| 上下文里放什么 | 完整数据块 | **引用**（文件路径 / 存储查询 / URL / 工具名） |
| 谁决定取什么 | 检索算法（离线定死） | **模型自己**（用工具决定） |
| 代价 | 快，但可能取错、可能过时 | 慢一点（多几次工具往返），但精准 |
| 典型载体 | 向量库 Top-K | `ls` / `grep` / `head` / `tail` / 文件系统 / NoteTool |

**类比**：预检索像"考试前把整本书背下来"，JIT 像"带着书和目录进考场，需要时翻到那一页"。

人类本来就是 JIT 的：我们不记全部信息，我们记**索引**（书签、文件夹、收件箱），需要时再去取。

### 1.3 元数据本身就是信号（这点很容易被忽略）

JIT 之所以高效，不只因为"按需"，还因为**引用本身携带语义**：

- `tests/test_utils.py` vs `src/core/test_utils.py` → 同样的文件名，暗示完全不同的用途；
- 文件**大小** → 暗示复杂度（几十行的脚本 vs 上万行的核心模块）；
- **时间戳** → 暗示时效性（上周改的 vs 三年前的）；
- **目录层级** → 暗示归属与职责边界。

模型不用读内容，光看"路径 + 大小 + 时间"就能做出**下一步该怎么读**的决策。这就是 **渐进式披露（Progressive Disclosure）**：

```
ls（看结构） → 按命名/大小/时间挑目标 → head/grep 局部读 → 只把相关片段带进上下文
```

每一层交互产生新信息，新信息反过来指导下一次取数——**上下文是一步步"长"出来的，不是一次性"灌"进去的**。

### 1.4 代价与最优解：混合策略

JIT 的代价是**多轮工具调用 = 更慢 = 更多 token 花在"探索"上**。所以工程上的常见最优解是混合：

- **前置加载少量高价值上下文**保值速度（README / 项目约定 / 核心接口签名）；
- **同时提供 `glob` / `grep` / `read` 等原语**让 Agent 自主深挖；
- 好处：绕开"索引过时"和"语法树解析成本"这两大沉没成本。

### 1.5 JIT 的落地载体（hello-agents 里的三个）

| 载体 | 作用 | 对应 JIT 的哪一环 |
|------|------|------------------|
| **TerminalTool** | `ls`/`cat`/`head`/`tail`/`grep`，带工作目录沙箱、危险命令拦截、输出长度限制 | **取数原语** |
| **NoteTool** | 结构化笔记（标题/内容/标签/时间/分类）持久化到磁盘，支持写/读/搜/列/改/删 | **外存（把结论搬出窗口）** |
| **ContextBuilder** | GSSC 流水线，把各路候选拼成最终上下文 | **装配器（决定最终看到什么）** |

> 一句话：**NoteTool 负责"把东西放出去"，TerminalTool 负责"需要时取回来"，ContextBuilder 负责"摆到桌面上摆成什么样"。**

## 二、GSSC 理论：四步把"候选信息宇宙"压成"一桌菜"

```
Gather（采买） → Select（挑菜） → Structure（摆盘） → Compress（打包）
```

| 阶段 | 一句话 | 失败后果 |
|------|--------|---------|
| **Gather** 把可能有用的信息找出来 | 多源汇集，容错 | 漏召回（该有的没有） |
| **Select** 决定哪些值得放进去 | 打分 + 过滤 + 预算内贪心 | 窗口被噪声淹没 |
| **Structure** 整理成模型易理解的格式 | 分区模板 | 模型分不清"哪是证据哪是要求" |
| **Compress** 确保最终不会过长 | 兜底截断/摘要 | 结构崩塌 / 关键信息丢失 |

### 2.1 统一中间表示：ContextPacket

GSSC 能跑通的前提是**先归一化**——不管信息来自系统指令、记忆、RAG 还是对话历史，先全变成同一种"信息包"：

```python
ContextPacket(
    content="...",           # 文本内容
    timestamp=datetime,      # 时间戳 → 算新近性
    token_count=123,         # token 数 → 算预算
    relevance_score=0.7,     # 相关性 0~1
    metadata={"type": "...", "priority": "..."}   # 类型标签 + 优先级
)
```

> 设计味道：**统一中间表示（IR）**。和第七章"万物皆为工具"是同一个思路——差异留在入口，处理逻辑只有一套。

### 2.2 Gather：多源汇集（关键在容错）

五个来源，按优先级：

1. **系统指令**：`relevance_score=1.0` 固定，**不参与评分**，永远保留；
2. **记忆检索**：`memory_tool.run({"action":"search","query":..., "limit":10, "min_importance":0.3})`；
3. **RAG 检索**：`rag_tool.run({"action":"search","query":..., "limit":5, "min_score":0.3})`；
4. **对话历史**：**只取最近 5 条**（`history[-5:]`），基础相关性 0.6；
5. **自定义信息包**：外部显式注入。

三个工程考虑（源码里看得很清楚）：

- **每个外部源都 try-except**：单个源挂了只打 WARNING，不影响整体 → 可用性优先于完整性；
- **系统指令标 priority=high**：它是"宪法"，永远不被预算淘汰；
- **历史限量 5 条**：历史最容易无限膨胀，先给它上硬闸。

> 💡 记忆和 RAG 的 `limit` 是"**多捞**"逻辑（10 / 5），因为后面 Select 还会筛——Gather 阶段的正确心态是**宁多勿漏**。

### 2.3 Select：核心中的核心（决定上下文质量）

这是整条流水线唯一的"取舍"环节，五步：

**① 先扣系统指令的预算**

```python
system_tokens = sum(p.token_count for p in system_packets)
remaining_tokens = available_tokens - system_tokens
if remaining_tokens <= 0:
    return system_packets   # 只返回系统指令 + 告警
```

> 顺序很讲究：**先给宪法留位，再分配剩余预算**。不然后面贪心可能把系统指令挤掉。

**② 相关性 relevance_score**

- 默认 0.5 的才重算（避免重复计算）；
- 示例用 **Jaccard 相似度**：分词后 `交集 / 并集`。
  - 优点：零依赖、可解释、够快；
  - 缺点：只抓词面，不抓语义 → **生产环境换成向量相似度**。

**③ 新近性 recency（指数衰减）**

```python
recency = math.exp(-0.1 * age_hours / 24)
recency = max(0.1, min(1.0, recency))   # 夹在 [0.1, 1.0]
```

- 24h 内几乎不掉分，之后平缓衰减；
- **为什么夹在 `[0.1, 1.0]` 而不是 `[0, 1]`**：老信息**不该被彻底归零**——"用户三个月前说自己是 Java 工程师"依然有用，衰减只是让它"更容易被挤掉"，不是"判死刑"。

**④ 综合分 + 阈值过滤**

```python
combined = relevance_weight * relevance + recency_weight * recency
if relevance >= min_relevance:   # 低于阈值直接丢
    keep
```

> **两个权重就是产品的"性格"**：  
> - 权重偏相关性 → 查知识库、查文档（**准**优先）；  
> - 权重偏新近性 → 聊天记忆、实时任务（**新**优先）。

**⑤ 排序 + 贪心填充**

```python
scored.sort(key=score, desc=True)
for score, packet in scored:
    if current + packet.token_count <= available:
        selected.append(packet); current += packet.token_count
    else:
        break   # 预算满，停
```

- **为什么贪心不最优**：这是 0/1 背包问题，最优解是 NP 的；贪心 **O(n log n)**、可解释、结果稳定，工程上远胜"数学最优但黑盒"；
- **注意 `break` 而不是 `continue`**：预算满了直接停，是"保持高分连续段"的取向——跳过低分小包硬填空隙反而会稀释信号。

**五步串起来的心智模型**：

```
宪法留位 → 打分（准 + 新）→ 阈值筛垃圾 → 高分优先往里塞 → 塞不下就停
```

### 2.4 Structure：把它们摆成模型能读懂的桌

按类型分组，套固定分区模板：

```
[Role & Policies]   ← system_instruction（我是谁、遵守什么）
[Task]              ← user_query（现在要干什么）
[Evidence]          ← rag_result / knowledge（外部证据，多篇用 --- 分隔）
[Context]           ← 记忆 / 对话历史（背景与来龙去脉）
[Output]            ← 输出要求
```

三个收益：

- **可读性**：人和模型都一眼看清结构；
- **可调试性**：答错了，一眼定位是证据烂、还是任务没说清、还是背景缺失；
- **可扩展性**：加新信息源 = 加一个分区，不动其它逻辑。

> 深层理由回到 Transformer：**注意力分配是可被结构引导的**。分区 = 给模型提供"该关注哪块"的显式线索；一坨没有边界的文本，注意力只能平均铺开，等于主动稀释。

### 2.5 Compress：兜底，不是常规路径

```python
if current_tokens <= max_tokens:
    return context            # 不超就不动
```

超了才压缩，策略是**按分区（`split("\n\n")`）逐段保留**：

- 能整段塞下 → 完整保留；
- 剩的空间 > 50 tokens → **部分截断**并标 `[... 内容已压缩 ...]`；
- 否则 break。

**原则：保持结构完整性**——宁可每块都留一点关键信息，也不要"某一块整个消失"。因为**丢一整个分区 = 模型失去一类视角**（比如完全没有 Evidence，它就只能瞎编）。

已知的简化（源码注释都写了）：

- token 计数是估算（中文 1 字 ≈ 1 token，英文 1 词 ≈ 1.3 token）→ 生产用真 tokenizer；
- 截断按字符比例估算 → 生产用 LLM 摘要（对应 9.2.4 的"压缩整合"）。

### 2.6 GSSC 与长时程三件套的对应关系

| 长时程手段（9.2.4） | GSSC 里对应 | 关键词 |
|-------------------|------------|--------|
| 压缩整合（Compaction） | **Compress** | 接力 |
| 结构化笔记（NoteTool） | **Gather** 的一个源 + 窗口外的外存 | 外存 |
| 子代理架构 | GSSC **外面**（子代理各自跑自己的 GSSC，只回传摘要） | 分工 |

> 所以 GSSC 不只服务单轮：子代理架构本质是"**每个子代理内部各跑一遍 GSSC，主代理只收压缩后的结论**"——同一套思想的不同尺度。

### 2.7 参数调优速查

| 参数 | 含义 | 调大 | 调小 |
|------|------|------|------|
| `max_tokens` | 上下文硬上限 | 信息更全，但慢 + 上下文腐蚀 | 更快更准，但可能漏料 |
| `reserve_ratio` | 给输出预留的比例 | 长回答场景（代码/长文） | 短答场景 |
| `min_relevance` | 相关性门槛 | 只留精料，抗噪 | 宁多勿漏，但易灌水 |
| `relevance_weight` / `recency_weight` | 准 vs 新 | 偏相关性=查知识/文档 | 偏新近性=聊天/实时 |
| `enable_compression` | 兜底开关 | 长任务必开 | 调试期可关（看真实长度） |

## 三、Transformer 架构：为什么"省上下文"不是运维细节，而是物理约束

> 详细版本见 [03-大语言模型基础](./03-大语言模型基础.md)，这里只讲**和上下文工程直接相关**的那部分。

### 3.1 一句话回顾

**Transformer = 自注意力（Self-Attention）+ 前馈网络（FFN）堆叠**，去掉 RNN 的时序依赖，让所有 token **两两直接建立关联**并可并行计算。

```
输入 → Embedding + 位置编码
     → [多头自注意力 → 残差+LayerNorm → FFN → 残差+LayerNorm] × N 层
     → 输出（Decoder-Only 下预测下一个 token，自回归）
```

### 3.2 自注意力：单头公式

每个 token 生成三个向量：

- **Q（Query 查询）**：我在找什么？
- **K（Key 键）**：我是什么、我能被谁匹配？
- **V（Value 值）**：我实际携带的信息

```text
Attention(Q,K,V) = softmax( Q·Kᵀ / √d_k ) · V
```

- `Q·Kᵀ` → 每个 token 对其它所有 token 的**相关性打分矩阵**（n×n）；
- `/√d_k` → 缩放，防止点积过大让 softmax 饱和（梯度消失）；
- `softmax` → 归一化成"注意力权重（总和为 1）"；
- `·V` → 按权重加权求和，得到该 token 的新表示。

**多头（Multi-Head）**：把 Q/K/V 分成 h 份并行算，各自关注不同子空间（语法、指代、语义……），再拼接投影。类比：多个"视角"同时看一句话。

**位置编码（Positional Encoding）**：注意力本身不认顺序，必须额外注入位置信息（正弦编码 → 可学习 → RoPE 旋转位置编码）。

**Decoder-Only + 因果掩码（Causal Mask）**：用上三角 `-∞` 遮罩，让每个 token 只能看**自己及之前**的 token——这就是"自回归生成"的底层保证，也是 GPT 系、Qwen、DeepSeek 的形态。

### 3.3 为什么 Transformer 直接推导出「上下文是有限资源」

这是本节最该记住的因果链 👇

**① n² 注意力 → 注意力被"拉薄"**

每个 token 的注意力权重总和恒定为 1。上下文从 1k 涨到 100k，**每个 token 能分到的平均权重缩小 100 倍**。

> 这就是"上下文腐蚀（Context Rot）"的机制解释：不是模型"忘了"，而是**每一份信息都被稀释了**。针堆找针基准（needle-in-a-haystack）里 token 越多召回越差，根子就在这里。

**② 训练分布偏短序列**

训练语料里短序列远多于长序列 → 模型对"极长依赖"的经验和专门参数都更少 → 长上下文下性能是**渐变下滑（performance gradient）**，而不是"陡崖式崩塌"。

**③ 位置编码外推有代价**

RoPE 类插值能让模型"适配"超出训练长度的序列，但会牺牲位置精度 → 越靠外的位置越"糊"。

**④ 结论（顺手记住这句话）**

> **Transformer 的注意力预算，就是上下文工程的物理上限。**  
> GSSC 的 Select 在做的"相关 + 新近加权、贪心填充"，本质就是**在替模型做注意力预算的分配决策**——把有限的 1.0 权重量，倾斜给信号密度最高的那几块 token。

### 3.4 Transformer 视角看 JIT 与 GSSC

| Transformer 特性 | 对上下文工程的含义 |
|-----------------|-------------------|
| 注意力总和恒为 1（n² 稀释） | 塞更多 ≠ 更好，**Select 是刚需** |
| 位置编码分辨率有限 | 关键信息**放前面/放明确分区**（Structure） |
| 因果掩码 / 自回归 | **历史越长，越要压**（Compress、历史只留 5 条） |
| 无状态（每次重算全序列） | 上一轮用过的信息若不再相关 → **不要重复塞**（JIT 按需取） |
| 上下文是"输入"，不是"记忆" | 记忆必须**外置**（NoteTool / MemoryTool） |
