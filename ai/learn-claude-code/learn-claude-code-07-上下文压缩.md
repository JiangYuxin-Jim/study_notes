# Learn Claude Code · 第七章：上下文压缩（Context Compression）

> 学习日期：2026-09-22
> 内容类型：AI 编程智能体（Coding Agent）工程实现原理
> 前置：前六章（Agent Loop / 工具调用 / 三层权限隔离 / 钩子函数 / TodoWrite / Subagent 与 Skill）
> 一句话：**第六章说"别让上下文被淹，换个窗口干活"；这一章讲的是"当主对话真的被塞满了，怎么在不丢信息的前提下把它瘦下来"——一套从轻到重的四级降级策略。**

---

## 一、为什么需要压缩

Agent 跑的轮次一多，上下文必然膨胀。膨胀的来源很具体，主要三类：

| 来源 | 典型症状 |
|------|----------|
| **工具调用结果** | 读了一个大文件、跑了一次 `grep`/`ls -R`、爬了一次网页，返回几万 token |
| **消息条数** | 几十轮对话堆在一起，每条都带着历史 |
| **单个消息内容** | 某一条消息本身就巨大（大文件内容、长日志） |

上下文窗口有硬上限，超了就报错/被截断，Agent 直接"失忆"或崩掉。所以压缩不是一个可选优化，而是**必须有的兜底机制**。

核心设计原则：**从最轻的手段开始试，不够再上更重的手段**——因为压缩本身就丢信息，能少丢就少丢。

---

## 二、⭐ 四种上下文压缩策略（从轻到重）

### 1️⃣ 工具调用结果压缩（截断）

**问题**：某次工具调用的返回结果太长。

**做法**：直接把最大的部分**丢掉（落盘/丢弃）**，只保留**前面的一些字符**。

```
[工具返回：30000 字符的文件内容]
        ↓ 截断
[前 N 个字符] ...（其余丢弃）
```

**特点**：
- **最轻**：只动单个工具结果，不动对话结构，不额外调 LLM，零成本零延迟
- **最粗暴**：丢的内容不可恢复（除非本来就有"落盘"）
- **适用**：结果大部分是冗余的（比如读了个大文件，其实只关心开头部分）

> 💡 这是四级里的**第一道闸门**——成本最低，所以最先触发。

---

### 2️⃣ 消息数量压缩（首尾保留）

**问题**：对话**消息条数**超过阈值（例如 50 条）。

**做法**：保留**最前面的少数几条**（例如 3 条） + **后面的多数几条**（例如 47 条），**掐掉中间**。

```
消息 1   ← 保留（3 条）   ┐
消息 2   ← 保留           │ 头部：通常是 system prompt、
消息 3   ← 保留           ┘ 初始任务设定等"根上下文"
消息 4   ← 丢弃（中间）   ┐
   ...                   │ 中段历史被裁掉
消息 5?  ← 丢弃           ┘
   ...
消息 50  ← 保留（47 条）  ┐
   ...                   │ 尾部：最近对话，最相关
消息 N   ← 保留           ┘
```

**为什么保留**最前面 + 最后面，掐中间？
- **头部**：system prompt、原始任务设定、关键约束——这些是"根"，丢了整个 Agent 就跑偏
- **尾部**：最近的对话轮次，与当前任务的**相关性最高**
- **中段**：既不是根、又不是最新，**信息价值密度最低**，是性价比最高的牺牲品

**特点**：
- 仍然**不调 LLM**，纯机械操作，成本极低
- 会丢中段信息，但通常可接受（中段往往是已经"消化"过的探索过程）

---

### 3️⃣ 消息内容压缩（引用化 / 分级降级）

**问题**：消息数量不算超标，但**内容总量**还是太大。

**做法（分两级，逐级加码）**：

**第一级：老工具调用结果 → 替换成文件路径**
- 把**已经用过的、老的**工具调用结果，从"内联的完整内容"**压缩成一个文件路径引用**
- 例如：原本内联 5000 字符的文件内容，变成 `见 /tmp/xxx.txt`
- 需要时 Agent 可以按路径重新读回来——**信息没真丢，只是从"常驻内存"变成了"按需取盘"**

**第二级：还是不够 → 把新的工具调用结果也压缩**
- 老的处理完了还超，那就对**新的**工具结果也动刀（同样引用化/精简）

**特点**：
- 比前两级更"聪明"：**保留了可恢复性**（路径可回溯）
- 逻辑是**"先老后新"**——老结果大概率已经用完不再需要，优先牺牲；新结果尽量保留原文
- 仍然是机械操作，不调 LLM

> 💡 这一级的设计哲学：**把上下文从"缓存"降级为"外存"**。工具结果本质是数据，数据不该常驻宝贵的上下文窗口。

---

### 4️⃣ LLM 摘要兜底（机械压缩全都不行时）

**问题**：前面三种**机械压缩**（截断 / 掐中间 / 引用化）都试过了，还是超。

**做法**：让 **LLM 把整个过去总结成"一张纸"**——用摘要替代原始历史。

```
[完整历史：几十轮对话 + 工具结果] 
        ↓ 交给摘要模型
[一页纸摘要] ← 用它替换掉整个历史
```

**关键细节：给摘要模型的输入本身也要裁剪** ⭐

摘要模型自己也有上下文上限，不可能把整个历史原封不动喂进去。所以喂给摘要模型的输入也要**按比例裁剪**：

- **取前面的 1/4**（上限的 25%）
- **取后面的 3/4**（上限的 75%）

```
摘要模型的输入预算（假设上限 = X）
┌──────────────┬────────────────────────────┐
│  前面的 1/4   │        后面的 3/4            │
│  (X × 0.25)  │       (X × 0.75)           │
└──────────────┴────────────────────────────┘
     根上下文            最近的历史
```

**为什么是 1/4 + 3/4 而不是对半分？**
- **后面（3/4）更重要**：越靠近现在的内容，与当前状态越相关，摘要时要抓住的"现状"都在尾部
- **前面（1/4）保底**：留住最初的 system prompt / 任务定义 / 关键约束，防止摘要跑题
- 这其实是策略 2️⃣"首尾保留"思想的**加权版本**——同样是头尾取舍，但给尾部更高的配额

**特点**：
- **最重**、也是**最后一招**：要额外调一次 LLM，有成本和延迟
- 带来**不可逆的信息损失**（摘要必然丢细节），但能一次性把上下文压到极小
- 是真正的**兜底机制**：前面三级是"减少信息量"，这一级是"把信息换成抽象"

## 三、四种策略总览对比

| 级别 | 策略 | 触发条件 | 手段 | 是否调 LLM | 信息可恢复性 | 成本 |
|------|------|----------|------|-----------|--------------|------|
| 1️⃣ | **工具结果压缩** | 单个工具结果太长 | 直接截断，保留前部 | ❌ | 低（丢就丢了）| 最低 |
| 2️⃣ | **消息数量压缩** | 消息条数 > 阈值（如50）| 保留头 3 条 + 尾 47 条，掐中间 | ❌ | 中（丢中段）| 极低 |
| 3️⃣ | **消息内容压缩** | 内容总量太大 | 老结果→文件路径，再不行压新结果 | ❌ | **高（路径可回溯）** | 低 |
| 4️⃣ | **LLM 摘要兜底** | 机械压缩全失效 | LLM 总结成一页纸（输入按 1/4 + 3/4 裁剪）| ✅ | 低（摘要丢细节）| 最高 |

**一句话记忆（降级链条）**：

> **先砍单条 → 再砍中段 → 再转外存 → 最后求 LLM 做摘要**

层层递进，**能用便宜的手段解决就绝不上贵的**。

## 四、设计思想提炼

### 1. 分级降级（Graceful Degradation）
不是"一超就摘要"，而是**四级递进**。因为每次压缩都丢信息：
- 前三级是**机械压缩**（确定性、零 LLM 成本）
- 第四级才是**语义压缩**（要调模型、不可逆）

### 2. "头尾优先"的取舍逻辑
策略 2 和策略 4 都体现同一个直觉：**上下文的两端比中段更有价值**。
- **头** = 身份与任务定义（不可丢）
- **尾** = 当前状态与最近交互（最相关）
- **中** = 已消化的过程（最可牺牲）

### 3. 缓存 vs 外存
策略 3 的"引用化"本质是**存储分层**：把不必常驻的信息从上下文窗口（贵、小）挪到文件系统（便宜、大），需要时再读回来。**这正是第六章 Subagent 思想的同源——都是"别让上下文装不该装的东西"**。

### 4. 摘要自身也要防溢出
策略 4 的"1/4 + 3/4 裁剪"揭示一个工程细节：**压缩工具自身也有上下文限制**，所以压缩操作是**递归的**——你要压缩上下文，得先保证喂给压缩器的输入不超限。

## 六、小结

- **上下文压缩 = 四级降级机制**，从轻到重：截断 → 掐中间 → 引用化 → 摘要
- **核心直觉**：头尾比中段重要；能用机械手段就别调 LLM；信息能从"内存"挪到"盘"就先挪
- **最重的兜底**：LLM 摘要，且喂给摘要模型的输入也要按 **前 1/4 + 后 3/4** 裁剪
- **本质**：上下文工程 = 在有限的窗口里，动态管理"什么信息值得常驻"
