## 一、前置知识：什么是 IO 模型

网络 IO 的核心问题：**应用进程如何等待数据从网卡/内核到达用户空间**。按等待方式不同，IO 模型可分为几类，Redis 网络模型最核心的讨论就围绕它们展开。

### 阻塞 IO（BIO）
- 进程发起 read 调用，**一直阻塞**等数据就绪，然后拷贝数据，才返回。
- 问题：一个线程一次只能处理一个连接，多连接要开多线程 → 线程开销大、上下文切换频繁。

### 非阻塞 IO（NIO）
- read 调用立即返回，若数据未就绪则返回错误（如 `EWOULDBLOCK`）。
- 进程需要**不断轮询**（忙等）判断数据是否就绪 → CPU 空转浪费。

### IO 多路复用（Multiplexing）⭐
- 用一个线程同时**监听多个文件描述符（FD）**的状态。
- 当某个/某些 FD 就绪（可读/可写/异常）时，内核**主动通知**应用进程去处理。
- 从"进程主动去问每个连接" → "内核帮你盯着所有连接，就绪了叫你"。**这是 Redis 网络高性能的核心**。

> 一句话：**阻塞 IO = 一连接一线程；非阻塞 IO = 忙轮询；多路复用 = 一个线程盯着所有连接，内核通知就绪。**

## 二、IO 多路复用的三种实现：select / poll / epoll

| 维度 | select | poll | epoll |
|------|--------|------|-------|
| 底层结构 | 位图（bitmap） | 链表 | **红黑树 + 就绪链表** |
| 最大连接数 | 受 FD_SETSIZE 限制（默认 1024） | 无上限 | 无上限（取决于内存） |
| 检查方式 | 每次调用**全量遍历**所有 FD 拷贝到内核 | 每次调用**全量遍历**所有 FD | 内核**注册后**只关心就绪的 FD（事件通知） |
| 拷贝开销 | 每次把 FD 集合从用户态拷贝内核态 | 每次全量拷贝 | 只拷贝新增/删除的 FD（epoll_ctl） |
| 触发方式 | 水平触发 LT | 水平触发 LT | **水平触发 LT + 边缘触发 ET** |
| 性能 | O(n) 遍历 | O(n) 遍历 | **O(1) 直接取就绪事件** |

### select
- 用**位图**存储要监听的 FD，每次调用把整张位图从用户态拷贝到内核态。
- 内核遍历所有 FD 检查就绪状态，返回后用户程序还要**再次遍历**找出就绪的 FD。
- 最大监听 FD 数受 **FD_SETSIZE**（1024）限制。

### poll
- 用**链表**存储 FD（没有 1024 限制），其余流程跟 select 类似，仍是**全量遍历** + **全量拷贝**。
- 解决了 select 的连接数上限问题，但性能仍是 O(n)。

### epoll（Linux 下 Redis 默认使用）⭐
- **epoll_create**：创建一个 epoll 实例（红黑树记录要监听的 FD）。
- **epoll_ctl**：注册/修改/删除要监听的 FD（**只传变化的 FD**，避免全量拷贝）。
- **epoll_wait**：阻塞等待，返回**就绪的 FD 列表**（内核直接告诉你哪些就绪，不用再全量遍历）。
- 水平触发 LT：只要 FD 还有数据可读就一直通知。
- 边缘触发 ET：只有 FD **状态发生变化**（从无到有）才通知一次，处理不及时可能漏。

> epoll 三大优点：**连接数无上限、事件驱动不遍历、只传变化不拷贝**。

## 三、Redis 的网络模型：事件驱动 + 单线程 Reactor

### Redis 是单线程吗？
- Redis 的核心（**命令执行**）是**单线程**的：所有命令在**一个主线程**里顺序执行，天然避免并发竞争，这也是它高性能的重要原因之一。
- 但**不是从头到尾只有一个线程**：后台有 BIO 线程（处理阻塞读写）、持久化（RDB/AOF）子进程、6.0 起的 IO 多线程等。

### 为什么单线程还这么快？
1. **纯内存操作**：数据全在内存，没有磁盘 IO 瓶颈。
2. **IO 多路复用**：单线程却能高效监听成千上万个连接（epoll）。
3. **事件驱动**：采用 Reactor 模式，主线程只处理"就绪的事件"，空闲时不空转。
4. **避免上下文切换和锁竞争**：单线程顺序执行，无色切换、无并发锁。

### Redis 事件处理器（基于 Reactor 模式）
Redis 基于自己的事件处理器来处理网络请求，主要有两类事件：

**文件事件（File Event）**—— 网络 IO 相关
- 基于 IO 多路复用（epoll 等）监听多个 socket FD 的**可读/可写**事件。
- 当某个 socket 可读（有新命令）或可写（可返回结果）时，触发对应的**事件处理器**。

**时间事件（Time Event）**—— 定时任务
- 用于处理周期性任务，如 **serverCron**（周期性执行）：过期键清理、AOF 刷盘、统计数据等。
- 类似定时器。

> 主线程在一个循环里：**通过多路复用等待文件事件 → 依次处理就绪的文件事件 → 间隔处理到期的时间事件**，周而复始。

### 命令执行主流程（一次请求）
1. 客户端连接 → epoll 监听到可读事件。
2. 主线程调用**读取事件处理器**，把请求数据读入输入缓冲区。
3. **命令解析** → 交到命令执行器（单线程顺序执行）。⭐ 这一步是单线程核心
4. 执行命令（操作内存数据结构）。
5. 结果写入**输出缓冲区**，触发可写事件，返回给客户端。

## 四、Redis 6.0：多线程 IO（可选开启）

### 为什么引入多线程？
- 单线程 + 多路复用处理**网络读写**本身高效，但**大量连接并发读写**时，内核读写数据并拷贝到用户态这一步骤会产生瓶颈。
- 命令执行**必须**单线程（保证原子性），但**网络 IO 读写**可以并行化。

### 6.0 的多线程 IO 模型
- 主线程负责**命令执行**（仍然单线程）。
- 用**额外的 IO 线程**并行处理**网络数据的读取和写出**（socket 读写、解析、序列化结果）。
- 通过 `io-threads` 配置（默认关闭，值为 1 即单线程）。

### 意义小结
- **6.0 之前**：网络读写 + 命令执行都是单线程。
- **6.0 之后**：网络 IO 可多线程并行（分担读写压力），**命令执行依旧单线程**（保证一致性）。
- 多线程的收益主要是**多核 CPU + 高并发连接/大流量读写**场景；纯计算型命令提升有限。

> ⚠️ 关键理解：**"多线程"指网络 IO 读写多线程，不是命令执行多线程。命令始终单线程顺序执行。**

## 五、核心要点速记

- **三种 IO 模式**：阻塞（一连接一线程）、非阻塞（忙轮询）、**多路复用（内核帮我盯连接，就绪通知）**。
- **select/poll/epoll**：前两者全量遍历+全量拷贝 O(n)；**epoll** 红黑树 + 事件驱动 O(1)，只传变化 FD，连接数无上限，支持 ET/LT。
- **Redis 高性能** = 纯内存 + **IO 多路复用(epoll)** + **事件驱动(single-threaded Reactor)** + 单线程免锁。
- **两类事件**：文件事件（socket 读写）、时间事件（serverCron 等定时任务）。
- **命令主流程**：读入缓冲区 → 解析 → **单线程执行** → 输出缓冲区返回。
- **6.0 多线程 IO**：仅**网络读写**可多线程（io-threads，默认关），**命令执行始终单线程**。
