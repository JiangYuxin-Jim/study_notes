## 一、批处理优化

Redis 处理指令本身很快，主要耗时在网络传输，所以把**多条指令批量传输**给 Redis 能大幅提升效率。

### 1. 单条 vs 批量执行

**单个命令执行流程**：客户端发送 → 服务端解析执行 → 返回响应，每次都有网络往返(RTT)。

**N 条命令依次执行**：N 次网络往返，耗时主要在**网络传输**。

**批量思路**：将多条指令一次打包发送，减少网络往返次数。

### 2. MSet 等批量命令（Mxxx）

Redis 提供很多 `Mxxx` 命令批量插入：
- `mset`（批量设 String）
- `hmset`（批量设 Hash）

**限制**：MSet 只能操作**部分数据类型**（主要是 String/Hash），无法覆盖复杂类型。

### 3. Pipeline（管道）

对**复杂数据类型的批处理**，建议用 **Pipeline**：
- 把多条命令放入管道，攒批后一次性执行。
- 消除多条命令的网络往返开销，大幅提升吞吐。

```java
Pipeline pipeline = jedis.pipelined();
for (int i = 1; i <= 100000; i++) {
    pipeline.set("test:key_" + i, "value_" + i);
    if (i % 1000 == 0) {
        pipeline.sync();   // 每攒 1000 条，批量执行一次
    }
}
```

### 4. 集群下的批处理 ⚠️

集群模式下，MSet / Pipeline 的**多个 key 必须落在同一个 slot（插槽）**，否则执行失败。而批量数据往往分散在不同节点，怎么办？4 种方案：

| 方案 | 思路 | 优缺点 |
|------|------|--------|
| **串行执行** | 一条条发 | 实现简单，但耗时过久 |
| **串行 slot** | 先按 slot 分组，相同 slot 一组，**串行**对每组做 Pipeline | 比串行快一些，但实现较复杂 |
| **并行 slot** | 按 slot 分组后，**并行**执行各组 | 耗时最短，但实现最复杂 |
| **hash_tag** | 用 `{}` 指定 key 有效部分，让 key 落在同一 slot（一次处理所有 key） | 耗时最短、实现简单；但会让所有 key 落在同一节点 → **数据倾斜** |

> **推荐**：一般用**并行 slot**（第三种）。hash_tag 虽简单但有数据倾斜风险。

**分组做法**：用 `ClusterSlotHashUtil.calculateSlot(key)` 计算每个 key 的 slot，按 slot 分组，再对每组执行 Pipeline / MSet。

**Spring 集群下**：`StringRedisTemplate.opsForValue().multiSet(map)` 底层通过 `SlotHash.partition()` 自动按 slot 分组，分组建并行执行。

## 二、服务端优化

### 1. 持久化配置建议

持久化保数据安全，但带来额外开销：
- **做缓存的 Redis 实例**：尽量不要开启持久化。
- **建议关闭 RDB**，使用 **AOF** 持久化。
- 利用脚本**定期在 slave 节点做 RDB**，实现数据备份。
- 设置**合理的 rewrite 阈值**，避免频繁 `bgrewriteaof`。
- 配置 `no-appendfsync-on-rewrite = yes`，**禁止 rewrite 期间做 AOF**，避免引起阻塞。

**部署建议**：
- 物理机预留足够内存，应对 fork 和 rewrite。
- 单个 Redis 实例内存上限不要太大（如 4G/8G），加快 fork、减少主从同步和数据迁移压力。
- 不要与 **CPU 密集型**应用部署在一起。
- 不要与**高硬盘负载**应用（数据库、消息队列）一起部署。

### 2. 慢查询优化

#### 什么是慢查询
**耗时超过阈值的命令**就叫慢查询（不一定是"很慢"的查询）。

**慢查询危害**：Redis 单线程，慢查询命令占用主线程执行 → 后续大量请求被**阻塞排队**，引起报错。

#### 相关配置
- `slowlog-log-slower-than`：慢查询阈值，单位微秒，默认 10000，**建议 1000**。
- `slowlog-max-len`：慢查询日志（本质队列）长度，默认 128，**建议 1000**。

修改：`config set slowlog-log-slower-than 1000`

#### 查看慢查询
- `slowlog len`：查询慢查询日志长度
- `slowlog get [n]`：读取 n 条慢查询日志
- `slowlog reset`：清空慢查询列表

### 3. 命令及安全配置 ⚠️

Redis 默认绑定 `0.0.0.0:6379`，暴露公网且未认证会有严重安全漏洞。

**漏洞成因**：
- Redis 未设置密码
- 利用 `config set` 动态修改配置
- 使用 **Root 账号**启动 Redis

**防范建议**：
- Redis 一定要**设置密码**。
- 线上禁用 `keys`、`flushall`、`flushdb`、`config set` 等命令（可用 `rename-command` 禁用）。
- `bind`：限制网卡，禁止外网网卡访问。
- 开启防火墙。
- 不要用 Root 账户启动 Redis。
- 尽量不用默认端口 6379。

### 4. 内存划分与内存配置

内存不足会导致 key 频繁被删、响应变慢、QPS 不稳。**内存使用率超 90%** 就要警惕。

#### Redis 内存三大部分
| 内存占用 | 说明 |
|----------|------|
| **数据内存** | 最主要部分，存键值信息。主要问题：BigKey、**内存碎片** |
| **进程内存** | 主进程自身运行占用（代码、常量池），约几兆，可忽略 |
| **缓冲区内存** | 客户端缓冲区、AOF缓冲区、复制缓冲区等，波动大，是重点分析对象 |

**内存碎片**：Redis 底层按固定档位分配（8/16/20...），如 key 只需 10 字节，会分配 16 字节，多出的 6 字节无法使用 → 碎片。

#### 查看命令
- `info memory`：查看内存分配情况
- `memory usage key`：查看单个 key 内存占用

#### 关键：客户端缓冲区
客户端缓冲区 = **输入缓冲区 + 输出缓冲区**：
- **输入缓冲区**：最大 1G 且**不能设置**，超了 Redis 直接断开（说明处理不过来）。
- **输出缓冲区**：可以设置。**处理大量 big value 时输出过多**，若缓冲区过大 / 无上限，内存可能被占满导致 Redis 断开。

**解决方案**：
1. 给输出缓冲区**设置大小上限**。
2. 增加带宽，避免大量数据超过承受能力。

（复制缓冲区 `repl-backlog-size` 默认 1mb，太小会导致频繁全量复制；AOF 缓冲区无法设上限——这两者一般不构成问题。）

## 三、集群最佳实践：集群还是主从

集群具备高可用、自动故障恢复，但使用不当会有诸多问题：

### 集群存在的问题
1. **集群完整性问题**：默认配置下，只要**任意一个插槽不可用，整个集群就停止对外服务**。→ 修改 `cluster-require-full-coverage no`，让部分 slot 不可用时集群仍可对外服务（可用性优先）。
2. **集群带宽问题**：节点间不断 Ping 确认状态，每次携带插槽信息+集群状态。节点越多数据量越大（10 节点约 1kb），带宽被 Ping 占满。
   - **解决**：避免大集群（<1000 节点，业务庞大则分多个集群）、避免单物理机跑太多实例、配置合适 `cluster-node-timeout`。
3. **命令集群兼容性问题**：批处理 key 必须同 slot（见上文）。
4. **lua 和事务问题**：lua 和事务要求**原子性**，key 不在一个节点就无法保证 → 集群下**无法执行 lua 和事务**。

### 集群还是主从？
- **单体主从 Redis** 已能达到**万级 QPS**，且具备很强的高可用。
- 主从能满足需求时，**尽量不搭集群**（集群复杂度高、问题多）。

## 四、核心要点速记

- **批处理**：MSet 只能 String/Hash；复杂类型用 **Pipeline**；**集群下 key 必须同 slot**。
- **集群批处理 4 方案**：串行 / 串行 slot / 并行 slot（推荐）/ hash_tag（有数据倾斜风险）。
- **持久化**：缓存实例少开持久化；关 RDB 用 AOF；slave 定期 RDB 备份；合理 rewrite 阈值。
- **慢查询**：`slowlog-log-slower-than`(默认10000建议1000)、`slowlog-max-len`(默认128建议1000)；单线程下慢查询会阻塞。
- **安全**：设密码、禁 keys/flushall/config set、限制 bind、开防火墙、别用 Root、别用默认端口。
- **内存**：数据/进程/缓冲区三部分；碎片是数据内存问题；重点防**客户端输出缓冲区**过大占满内存。
- **集群 vs 主从**：主从够用就别搭集群；改 `cluster-require-full-coverage no` 保证可用性；集群无法执行 lua/事务。
