# 14 - Redis 哨兵（Sentinel）与分片集群（Cluster）

> 📅 2026-08-03 | 🏷️ Redis / 高级篇 / 高可用 / 分片集群

---

## 一、为什么需要哨兵

上一课的主从复制解决了**数据备份**和**读扩展**，但有个硬伤：**master 挂了谁来接管？**

如果 master 宕机，虽然 slave 上还有完整数据，但**写操作全部瘫痪**，需要人工手动把某个 slave 提升为 master，再改客户端的连接地址——整个过程无法自动完成。

哨兵（Sentinel）就是来解决这个问题的：**监控 + 自动故障转移**，让 Redis 真正具备高可用（HA，High Availability）。

---

## 二、哨兵 Sentinel

### 2.1 哨兵的三大作用

1. **监控**：Sentinel 以固定频率（默认 1 秒）向 master/slave 发送 PING，检测它们是否存活。
2. **自动故障转移（failover）**：当 master 被判定客观下线后，自动从 slave 中**选举出新的 master**，并把其他 slave 重新指向新 master。
3. **通知**：故障转移完成后，通过**发布订阅（Pub/Sub）**把新的 master 地址推送给客户端，客户端自动改连。

### 2.2 主观下线（SDOWN）与客观下线（ODOWN）

故障判定分两步，防止误判：

- **主观下线（Subjective DOWN）**：单个 Sentinel 自己判断。它给 master 发送 PING，若在 `down-after-milliseconds` 内没收到有效回复，就主观认为该 master 下线。
- **客观下线（Objective DOWN）**：**多个 Sentinel 达成共识**。当主观判断 master 下线的 Sentinel 数量达到 `quorum`（法定人数，如 2 个）时，才升级为客观下线，触发真正的故障转移。

> 💡 为什么要 quorum？因为单个 Sentinel 的网络抖动或 GC 停顿可能导致**误判**，需要多数派确认才安全，避免把健康的 master 误杀。

### 2.3 哨兵的选主规则（选举新 master）

故障转移时，从所有健康的 slave 中按如下优先级选出新 master：

1. **排除**：主观下线、断线超时、未返回有效回复的 slave。
2. **salve-priority 最小**：`slave-priority` 配置值越小，优先级越高（可手动指定某台机器优先当主）。
3. **复制偏移量最大**：offset 越大说明数据越新，选它当主**数据丢失最少**。
4. **runid 最小**：若上面都相同，选 runid 最小的（随机兜底）。

### 2.4 哨兵的高可用部署

- 哨兵通常部署 **奇数个**（如 3 个），保证能形成**多数派**，避免脑裂（split-brain，即出现两个 master）。
- 哨兵自身也要保证高可用，不能单点。
- `quorum` 一般设为半数以上，例如 3 个哨兵可设 quorum=2。

**sentinel.conf 关键配置：**
```
# 监控主节点：sentinel monitor <名称> <ip> <port> <quorum>
sentinel monitor mymaster 127.0.0.1 6379 2

# 主观下线判定超时时间（毫秒）
sentinel down-after-milliseconds mymaster 5000
```

**启动哨兵：**
```bash
# 方式一
redis-sentinel sentinel.conf

# 方式二
redis-server sentinel.conf --sentinel
```

### 2.5 哨兵模式的故障转移流程（总结）

```
master 宕机
  → 多个 Sentinel 判定主观下线，数量达到 quorum → 升级为客观下线
  → Sentinel 内部选举出一个 leader 负责本次转移
  → 从健康 slave 中按 priority → offset → runid 选出新 master
  → 其他 slave 执行 slaveof 指向新 master
  → Pub/Sub 通知客户端新 master 地址
  → 故障转移完成，集群恢复可用
```

## 三、分片集群 Redis Cluster

### 3.1 为什么需要分片

即使有了**主从 + 哨兵**，解决了高可用，但**单个 master 的内存容量和写并发仍有上限**：

- 内存受限于单台机器，数据量大装不下。
- 所有写操作都集中在 master 单点上，写并发无法横向扩展。

分片集群（Cluster）把数据**分片存储**在多台 master 上，每台 master 再配若干 slave，实现**水平扩展**——既扩容量，又扩写并发，还保持高可用。

### 3.2 插槽（Slot）分片机制

Redis Cluster 把数据空间划分为 **16384 个哈希槽**（hash slot）：

```
key 归属的槽位 = CRC16(key) % 16384
```

- 每个 master 负责**一段连续的槽位区间**（例如 3 主：0~5460、5461~10922、10923~16383）。
- 写入某个 key 时，先算它落到哪个槽，再由负责该槽的 master 处理。
- 只要保证 **16384 个槽全部被覆盖**，数据就能完整分到各个节点。

### 3.3 多主多从

一个典型的 3 主 3 从集群：

```
Master-A(槽0~5460)  ←→  Slave-A1
Master-B(槽5461~10922) ←→ Slave-B1
Master-C(槽10923~16383) ←→ Slave-C1
```

- 3 个 master 平分 16384 个槽位，都能接受写请求 → 写并发 ×3。
- 每个 master 配一个从节点 → 任意主挂了，从节点自动顶上，高可用不丢。

### 3.4 集群重定向（MOVED / ASK）

客户端访问 key 时，当前节点可能不负责该 key 所在的槽，此时节点返回重定向：

- **MOVED**：客户端访问一个**已固定归属**其他节点的 key，节点返回该 key 的槽号 + 目标节点地址，客户端**永久**重定向过去访问。
- **ASK**：槽位**正在迁移**过程中，客户端带 `ASKING` 临时访问目标节点一次。

> 客户端一般会缓存「槽号 → 节点」的映射表，避免每次重定向，提升访问效率。

### 3.5 分片集群的优势

1. **写并发水平扩展**：多台 master 同时可写，突破单点写瓶颈。
2. **海量数据存储**：内存分散在多台机器，支持更大数据量。
3. **高可用**：每个主节点都有从节点，主挂自动切换，数据不丢、服务不断。

## 四、生产环境多级缓存架构（最佳实践）

真正的生产高并发架构，往往不止 Redis，而是**多级缓存**层层递进：

```
浏览器/CDN
  → Nginx 本地缓存（Lua + OpenResty）
    → Redis 集群（分布式缓存，扛住大多数热点请求）
      → 数据库（Redis 未命中的回源，只承担少量请求）
```

配套手段：
- **缓存预热（Cache Preheating）**：系统启动时把热点数据提前写入 Redis，避免冷启动打崩 DB。
- **缓存同步（Cache Aside / Canal）**：DB 变更后，通过 Canal 监听 binlog 增量更新 Redis 缓存。
- **缓存降级**：Redis 或下游故障时启用降级策略，保证核心业务可用。

## 五、演进路线总结

```
单机 Redis
  └→ 主从复制      解决：备份 + 读扩展（但 master 挂了要手动处理）
      └→ 哨兵      解决：自动故障转移，高可用（但 master 写入仍是单点瓶颈）
          └→ 分片集群  解决：多主多从 + 槽位分片，水平扩展写并发和海量数据
```

---

## 六、核心要点速记

- **哨兵**：监控 + 自动故障转移 + 通知，让 Redis 高可用。
- 判定分**主观下线**（单节点）和**客观下线**（quorum 多数派），避免误判。
- 选主顺序：**priority → offset → runid**。
- **分片集群**：16384 个槽，`CRC16(key) % 16384` 定位，多主多从。
- 集群重定向：**MOVED**（固定归属）/ **ASK**（迁移中）。
- 生产架构追求**多级缓存 + 预热 + 同步 + 降级**。
