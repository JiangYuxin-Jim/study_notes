# 10 - UV 统计

> 📅 2026-07-30 | 🏷️ Redis / HyperLogLog / PF / 基数统计

---

## 业务场景

统计页面的 UV（Unique Visitor，独立访客）。同一个用户一天多次访问只算一次。

### UV vs PV

| 指标 | 含义 | 去重？ | 数据量 |
|------|------|--------|--------|
| PV | 页面浏览量 | 不 | 大（每次算一次） |
| UV | 独立访客数 | 是 | 小（去重后） |

## 传统方案的问题

### SQL 方案
```sql
SELECT COUNT(DISTINCT user_id) FROM tb_log WHERE page_id = ? AND date = ?
```
问题：数据量大了 COUNT(DISTINCT) 性能很差。

### Set 方案
```java
Set<Long> uvSet = new HashSet<>();
uvSet.add(userId); // 访问时加进去
return uvSet.size();
```
问题：百万级 UV 时，Set 内存占用极大。

### BitMap 方案
每个用户分配一个 bit 位，32 亿用户 = 512MB
问题：用户量大时 BitMap 也撑不住。

## HyperLogLog（HLL）方案

**核心思想**：用概率算法估算基数（去重后的数量），精度可接受但内存极小。

| 方案 | 存储 | 误差 | 适用 |
|------|------|------|------|
| Set | O(n) | 精确 | 小规模 |
| BitMap | O(n/8) | 精确 | 中等规模 |
| HyperLogLog | ~12KB | ~1% 误差 | 大规模计数 |

**HyperLogLog 固定只占 12KB 内存**，无论统计 100 个还是 10 亿个 UV。

## HyperLogLog 原理（简版）

### 伯努利过程
- 抛硬币，直到第一次出现正面
- 最大抛掷次数 ≈ 2^k（估算基数）

### 核心思路
1. 将用户 ID 通过 Hash 函数化为 64 位二进制
2. 看这个二进制串末尾连续 0 的个数 k
3. 如果某用户末尾有 k 个 0，则基数大约为 2^k
4. 取多个桶（16384 个）的平均值，降低误差

### 为什么不精确？
- 基于概率估算，不是精确计数
- 但 16384 个桶 + 调和平均修正后，误差约 0.81%
- 对于 UV 统计来说，这个精度完全够用

## Redis 命令

```bash
# 添加元素
PFADD key element [element ...]

# 统计基数
PFCOUNT key [key ...]

# 合并多个 HyperLogLog
PFMERGE destkey sourcekey [sourcekey ...]
```

### 代码示例

```java
// 统计页面 UV
String key = "uv:page:" + pageId + ":" + today;
stringRedisTemplate.opsForHyperLogLog()
    .add(key, userId.toString());

// 查询 UV
Long uv = stringRedisTemplate.opsForHyperLogLog()
    .size(key);

// 合并多天 UV
stringRedisTemplate.opsForHyperLogLog()
    .union("uv:page:" + pageId + ":weekly", key1, key2, key3);
```

## HyperLogLog 在项目中的实际应用

### 黑马点评项目

在项目中有专门的 UVController：

```java
@PostMapping("/uv")
public Result addUV(@RequestParam("pageId") Long pageId) {
    // 从请求头或登录态获取用户标识
    String userId = UserHolder.getUser().getId().toString();
    String key = "uv:" + pageId + ":" + LocalDate.now();
    stringRedisTemplate.opsForHyperLogLog().add(key, userId);
    return Result.ok();
}

@GetMapping("/uv/{pageId}")
public Result getUV(@PathVariable Long pageId) {
    String key = "uv:" + pageId + ":" + LocalDate.now();
    Long uv = stringRedisTemplate.opsForHyperLogLog().size(key);
    return Result.ok(uv);
}
```

### 生产环境使用场景

| 场景 | 说明 |
|------|------|
| 页面 UV | 每天页面独立访客数 |
| 活动 UV | 参与活动的独立用户数 |
| 搜索 UV | 独立搜索用户数 |
| DAU/MAU | 日活/月活用户数（合并多天 PFMERGE） |
| 频道 UV | 各频道的独立用户数 |

## PFCOUNT 的多 key 合并

```bash
# 计算单天 UV
PFADD uv:20260730 user1 user2 user3
PFCOUNT uv:20260730  # 3

# 计算多天 UV（自动合并去重）
PFCOUNT uv:20260729 uv:20260730  # 自动合并，用户不重复计数

# 永久保存合并结果
PFMERGE uv:week1 uv:20260728 uv:20260729 uv:20260730
PFCOUNT uv:week1
```

**注意**：`PFMERGE` 是 O(n) 操作，n 为 HyperLogLog 数量。

## HyperLogLog 的局限性

| 局限 | 说明 |
|------|------|
| 只能估算 | 无法精确知道哪些用户访问了 |
| 无法反向查询 | 不支持查某个元素是否在集合中 |
| 小基数误差大 | 基数 < 100 时误差可能较大 |
| 不可删除 | 一旦添加无法移除某个元素 |

## 与 BitMap 的配合

实际项目中，常同时使用：

```
BitMap → 判断某个用户是否访问过（精确判断存不存在）
HLL    → 统计 UV 总数（快速估算不精确求谁）
```

## 总结

| 知识点 | 核心要点 |
|--------|---------|
| HLL 本质 | 概率算法估算基数 |
| 内存 | 固定 ~12KB，无论数据多大 |
| 误差 | ~0.81% |
| 命令 | PFADD / PFCOUNT / PFMERGE |
| PFCOUNT 多 key | 自动合并去重 |
| 适用场景 | 大规模 UV 统计 |
| 不适用 | 需要精确计数、需要反向查询是否存在 |
