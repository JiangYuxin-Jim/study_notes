## 1. Redis 单机的问题

单机 Redis 在生产环境中面临三大问题：

| 问题 | 问题描述 | 影响 |
|------|---------|------|
| **数据丢失** | 服务器宕机，内存数据全部丢失 | 业务中断 |
| **并发能力** | 单机 Redis QPS 约 10 万，但高并发场景不够 | 请求堆积 |
| **存储容量** | 单机内存有限（一般几十 GB） | 存不下海量数据 |
| **单点故障** | Redis 挂了整个缓存层就挂了 | 所有流量打到 DB，雪崩 |

**解决方案对应关系：**

| 问题 | 解决方案 |
|------|---------|
| 数据丢失 | RDB + AOF **持久化** |
| 并发能力 | **主从架构**（读写分离） |
| 可用性 | **哨兵模式**（自动故障转移） |
| 存储容量 | **Cluster 集群**（分片存储） |

## 2. Redis 持久化（回顾与深入）

### 2.1 RDB（Redis Database Backup）

RDB 是 Redis 的**快照**持久化方式，在一定间隔内将内存数据**全量**写入磁盘。

```redis
# redis.conf 配置
save 900 1        # 900秒内至少1个key被修改 → 快照
save 300 10       # 300秒内至少10个key被修改 → 快照
save 60 10000     # 60秒内至少10000个key被修改 → 快照

# 手动触发
SAVE              # 同步阻塞，生产不用
BGSAVE            # fork子进程，异步，推荐方式
```

**RDB 执行流程：**
```
1. fork() 创建子进程（阻塞主进程毫秒级）
2. 子进程共享内存（写时复制 COW）
3. 子进程将内存数据写入临时文件
4. 原子替换旧 RDB 文件
```

| 特性 | RDB |
|------|-----|
| 文件大小 | 小（二进制压缩） |
| 恢复速度 | 快（直接加载） |
| 数据完整性 | 可能丢最后一次快照后的数据 |
| 对性能影响 | fork 时短暂阻塞，子进程 COW 不阻塞主进程 |

### 2.2 AOF（Append Only File）

AOF 记录**每一条写命令**到日志文件中，重启时重放命令恢复数据。

```redis
# redis.conf
appendonly yes         # 开启 AOF
appendfsync always     # 每次写入都同步（最安全，最慢）
appendfsync everysec   # 每秒同步一次（折中，推荐）
appendfsync no         # 由操作系统决定（最快，最不安全）
```

**AOF 重写机制（BGREWRITEAOF）：**
```
AOF 文件越来越大的问题 → 后台重写

例如：
SET key "a"  → 写入 AOF
SET key "b"  → 写入 AOF
SET key "c"  → 写入 AOF

重写后 → 只保留一条：SET key "c"
```

**AOF 执行流程：**
```
命令执行 → 追加到 aof_buf → 同步到磁盘（按 appendfsync 策略）
                                 ↓
重写时：fork 子进程，读取当前内存状态，生成最小命令集
```

### 2.3 RDB vs AOF

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 文件大小 | 小 | 大（但可重写） |
| 恢复速度 | 快 | 慢（需重放命令） |
| 数据安全性 | 可能丢较多数据 | 最多丢 1 秒（everysec） |
| 对性能影响 | fork 阻塞 + IO | 写操作有额外 io（折中可接受） |

**实际选择：两者都用**
- RDB：快速恢复 + 备份
- AOF：数据安全保障（最多丢 1 秒）

## 3. 主从架构（读写分离）

### 3.1 什么是主从？

```
                    ┌──────────┐
                    │  主节点    │ ← 负责写（SET/DEL/...）
                    │ (Master) │
                    └────┬─────┘
                         │ 数据同步
              ┌──────────┼──────────┐
              │          │          │
          ┌──┴──┐   ┌──┴──┐   ┌──┴──┐
          │ 从1  │   │ 从2  │   │ 从3  │ ← 负责读（GET/...）
          │Slave│   │Slave│   │Slave│
          └─────┘   └─────┘   └─────┘
```

### 3.2 配置方式

```bash
# 在从节点上执行
SLAVEOF master_ip master_port
# 或在 redis.conf 中配置
replicaof master_ip master_port
```

### 3.3 全量同步 vs 增量同步

#### 全量同步（首次连接 / 断连恢复失败时）

```
主节点：
1. 执行 BGSAVE 生成 RDB 快照
2. 同时将期间的写命令记录到 replication buffer
3. 将 RDB 文件发给从节点
4. 从节点清空旧数据，加载 RDB
5. 主节点发送 replication buffer 中的增量命令
```

#### 增量同步（断线重连时）

```
从节点断开期间（默认 1 分钟内），主节点将写命令记录在 repl_backlog_buffer 中
从节点重连后，通过 offset 同步缺失部分
```

### 3.4 主从同步中的关键参数

| 参数 | 作用 |
|------|------|
| repl_backlog_buffer | 主节点维护的固定大小环形缓冲区（默认 1MB） |
| repl_backlog_size | 缓冲区大小，建议设置足够大的值（网络差时调大） |
| master_repl_offset | 主节点当前写入位置 |
| slave_repl_offset | 从节点已同步位置 |
| repl_backlog_histlen | 缓冲区有效数据长度 |

**如果 slave_repl_offset 落后 master_repl_offset 超过 repl_backlog_size → 无法增量同步 → 触发全量同步**

## 4. 哨兵模式（Sentinel）

### 4.1 主从的问题

```
主节点宕机 → 从节点不会自动上位
需要人工操作：手动 SLAVEOF NO ONE 提升某个从节点为主节点
手工切换间隔 → 业务中断
```

### 4.2 哨兵的作用

哨兵是 Redis 提供的**高可用**方案，自动监控并完成**故障转移**：

```
┌──────────────────────────────────────┐
│           哨兵集群（至少3个实例）       │
│  ┌────────┐  ┌────────┐  ┌────────┐ │
│  │Sentinel1│  │Sentinel2│  │Sentinel3│ │
│  └────┬───┘  └────┬───┘  └────┬───┘ │
│       │           │           │      │
└───────┼───────────┼───────────┼──────┘
        │           │           │
        ▼           ▼           ▼
   ┌────────┐ ┌────────┐ ┌────────┐
   │ Master  │ │ Slave1 │ │ Slave2 │
   │ (主)    │ │ (从)   │ │ (从)   │
   └────────┘ └────────┘ └────────┘
```

### 4.3 哨兵的三大职责

| 职责 | 说明 |
|------|------|
| **监控** | 向所有 Redis 实例发送 PING，检测存活 |
| **选举** | 主节点故障时，自动选举新主节点 |
| **通知** | 通知客户端新主节点的地址 |

### 4.4 故障转移流程

```
1. 主观下线
   哨兵 A 发现 Master 超时未响应 PING → sentinel down

2. 客观下线
   其他哨兵也发现 Master 挂了 → 多数哨兵认同 → sdown → odown

3. 选举 Leader 哨兵
   哨兵集群通过 Raft 算法选出一个 Leader 执行故障转移

4. 选新主节点
   规则：从优先级高 → 数据最完整 → 从节点 ID 最小
   向该从节点发送 SLAVEOF NO ONE → 升为主

5. 通知其他从节点
   其他从节点执行 SLAVEOF new_master

6. 原主恢复
   原主恢复后，自动成为新主的从节点
```

### 4.5 Redis 哨兵实现高可用的不足

| 不足 | 说明 |
|------|------|
| **不是强一致** | 主从异步复制，主挂了没同步完的数据会丢失 |
| **无数据分片** | 所有节点存全量数据，容量受限于单机内存 |
| **脑裂风险** | 网络分区可能导致两个以为自己是主的节点 |

## 5. Cluster 集群模式

### 5.1 为什么需要 Cluster

```
单机 Redis 内存 16GB → 存不下
主从 + 哨兵 → 仍然是每台节点存全部数据 → 容量没扩展

需要：数据分片（Sharding）→ 每个节点只存一部分数据
```

### 5.2 Cluster 架构

```
Client
 │
 ├───→ 节点1 (0-5460 hash slot)
 ├───→ 节点2 (5461-10922 hash slot)
 └───→ 节点3 (10923-16383 hash slot)
```

- Redis Cluster 将**所有 key 映射到 16384 个哈希槽**
- 每个节点负责一部分槽位
- 客户端访问任一节点，如果 key 不在该节点，返回 MOVED 重定向

### 5.3 数据分片算法

```java
// CRC16(key) % 16384 = hash slot
// 例如：
// CRC16("user:1001") % 16384 = 1234 → 节点1
// CRC16("user:1002") % 16384 = 9000 → 节点2

// 特点：
// - 同一 key 永远落在同一节点
// - 支持 hash tag：{xxx} 使不同的 key 落在同一节点
//   如 {order}:1001 和 {order}:2001 都会落在同一节点
//   方便事务和批量操作
```

### 5.4 集群通信：Gossip 协议

节点之间通过 Gossip 协议交换状态信息：

```
节点 A ──→ 节点 B：发送自己的状态 + 随机其他节点状态
节点 B ──→ 节点 C：发送自己的状态 + 随机其他节点状态
...
信息像"流言"一样在集群中传播，最终所有节点达成一致
```

### 5.5 集群故障转移

```
集群中每个节点会监听其他节点
如果半数以上主节点认为某节点挂了 → 标记为 FAIL
如果该节点有从节点 → 从节点竞选 → 升为主

注意：
Cluster 模式下不需要 Sentinel
Cluster 自带故障检测和自动故障转移
```

### 5.6 三种部署方案对比

| 特性 | 主从 | 哨兵 | Cluster |
|------|------|------|---------|
| 容灾 | 手动切换 | 自动故障转移 | 自动故障转移 |
| 写扩展 | 无 | 无 | 数据分片（写扩展） |
| 读扩展 | 有（从节点读） | 有（从节点读） | 有（分片并行读） |
| 容量扩展 | 无 | 无 | 水平扩容 |
| 配置复杂度 | 低 | 中 | 高 |
| 数据一致性 | 异步复制，可能丢数据 | 同左 | 同左 |

## 6. 多级缓存架构

### 6.1 为什么需要多级缓存？

单靠 Redis 缓存还不够，因为：
- **Redis 本身也有网络 IO 开销**（每次查询都走网络）
- **Redis 也可能崩**（哨兵切换期间不可用）

多级缓存 = **本地缓存 + Redis 缓存** 双重保障

### 6.2 架构

```
用户请求
    │
    ▼
┌──────────┐
│  浏览器缓存  │ ← CDN / 强缓存（静态资源）
└──────────┘
    │ 未命中
    ▼
┌──────────┐
│  Nginx 缓存  │ ← Nginx 本地缓存（OpenResty + Lua）
└──────────┘
    │ 未命中
    ▼
┌──────────┐
│  Redis 缓存  │ ← 分布式缓存
└──────────┘
    │ 未命中
    ▼
┌──────────┐
│  MySQL     │ ← 最终数据源
└──────────┘
```

### 6.3 Nginx + Lua 本地缓存

```lua
-- OpenResty / nginx.conf
-- 使用 shared_dict 做本地缓存

-- 查询本地缓存
local item = ngx.shared.my_cache:get("item:1001")
if item then
    ngx.say(item)
    return
end

-- 本地未命中 → 查 Redis
local redis = require("resty.redis")
local red = redis:new()
red:set_timeout(1000)
red:connect("127.0.0.1", 6379)

local data = red:get("item:1001")
if data ~= ngx.null then
    -- 设置本地缓存（10秒过期）
    ngx.shared.my_cache:set("item:1001", data, 10)
    ngx.say(data)
    return
end

-- Redis 也未命中 → 查 MySQL
-- ...
```

### 6.4 本地缓存 vs Redis 缓存

| 特性 | 本地缓存（Nginx/Java） | Redis 缓存 |
|------|------------------------|------------|
| 速度 | 纳秒级（内存直接读） | 微秒级（网络 IO） |
| 容量 | 受限于单机内存（几GB） | 集群可扩展到 TB 级 |
| 一致性 | 多节点间数据不一致 | 统一存储，强一致性 |
| 更新 | 需广播通知各节点 | 直接更新 Redis |
| 适用 | 热点数据（QPS 极高） | 全量缓存数据 |

### 6.5 缓存更新策略

| 策略 | 做法 | 特点 |
|------|------|------|
| **主动更新（Cache Aside）** | 更新 DB → 删除/更新 Redis | 最常用，实现简单 |
| **被动过期（TTL）** | Redis key 设过期时间，自动失效 | 简单但数据有时效性 |
| **异步更新（MQ）** | DB 变更 → 发 MQ → 消费更新缓存 | 解耦，但延迟稍高 |
| **Canal 监听 binlog** | MySQL binlog → Canal → 更新 Redis | 无侵入，但需要 Canal 组件 |

## 7. Redis 最佳实践

### 7.1 键值设计

```markdown
✅ 好的 key 设计：
- 业务名:表名:id  →  order:order:1001
- 层级清晰，见名知意
- 不宜过长（占用内存）
- 使用 {} 做 hash tag（Cluster 环境）

❌ 坏的 key 设计：
- a               → 无意义
- UserName        → 大小写不统一，不好记忆
- 订单1001的信息  → 含中文
- orderList:1001  → 太泛，type 不明确
```

### 7.2 Big Key 问题

```markdown
什么是 Big Key？
- String 类型 value 超过 10KB
- 集合类型元素超过 5000 个（List/Set/ZSet/Hash）

危害：
- 删除 Big Key 会长时间阻塞 Redis（DEL 是 O(n)）
- 网络传输大 value 增加延迟
- 内存不均匀分配到某些节点（Cluster 场景）

解决：
- 拆分：hash 拆成多个小 hash，list 分页
- 压缩：大文本用 snappy/gzip 压缩后存
- 注意删除：用 UNLINK（异步删除）
```

### 7.3 热点 Key

```markdown
什么是热点 Key？
- 某个 key 被超高并发访问（如：秒杀商品、明星新闻）

危害：
- 单个 Redis 节点 CPU 打满
- Redis Cluster 中某一节点成为瓶颈

检测：
- 客户端统计访问频次
- Redis 4.0+ 的 hotkeys 参数（redis-cli --hotkeys）

解决：
- 复制多份：key 加后缀分散到不同节点（如 item:1001:1, item:1001:2）
- 本地缓存：热点数据本地缓存命中
- 读写分离：从节点分摊读压力
```

### 7.4 慢查询

```redis
# 查看慢查询配置
CONFIG GET slowlog-log-slower-than  # 默认 10000 微秒（10ms）
CONFIG GET slowlog-max-len           # 默认 128 条

# 查看慢查询日志
SLOWLOG GET 10

# 常见慢查询原因
# 1. KEYS *        → 用 SCAN 替代
# 2. 大 key 的 DEL → 用 UNLINK
# 3. SORT          → 谨慎使用大数据集排序
# 4. 复杂 Lua 脚本 → 保持脚本简短
```

### 7.5 内存优化

```markdown
节省内存的技巧：

1. 不要存大对象
   - 用户 ID 存 int 而不是 string
   - 用 Hash 的 ziplist 编码（小 hash 省内存）

2. 合理设置过期
   - 不用的数据及时过期
   - 设置合理的 maxmemory + 淘汰策略

3. 使用更高效的类型
   - List 代替 Set（不需要去重时）
   - IntSet 编码的 Set（全是数字时）
   - ZipList 编码的 Hash/List/ZSet

4. 淘汰策略
   - volatile-lru：对有过期时间的 key 做 LRU（最常用）
   - allkeys-lru：所有 key 做 LRU
   - volatile-ttl：优先淘汰快过期的
   - 默认：noeviction（不淘汰，写满报错）
```

## 8. 关键知识点总结

| 内容 | 要点 |
|------|------|
| 持久化 | RDB（快照）+ AOF（日志），配合使用 |
| 主从架构 | 读写分离，全量同步+增量同步 |
| 哨兵模式 | 自动故障转移，Raft 选举 |
| Cluster 集群 | 16384 哈希槽分片，Gossip 通信 |
| 多级缓存 | Nginx 本地缓存 + Redis + Canal 同步 |
| Big Key | 拆、压缩、UNLINK 删除 |
| 热点 Key | 本地缓存、Key 打散 |
| 淘汰策略 | volatile-lru 最常用 |
| 内存优化 | ziplist、intset 编码节省内存 |
