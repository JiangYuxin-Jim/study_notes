## 一、为什么需要持久化

Redis 是**内存数据库**，数据默认存在内存里，一旦进程退出 / 宕机 / 重启，数据全部丢失。

```
内存（易失）               磁盘（持久）
Redis 进程 ──宕机──▶ 内存数据全部丢失
                   如果要保住数据，就必须在宕机前把数据写到磁盘
```

### 两种持久化方式

| 方式 | 全称 | 核心思想 | 可靠性 | 性能 |
|------|------|----------|--------|------|
| **RDB** | Redis DataBase | 定期把内存数据**快照**写入磁盘（二进制） | 可能丢最后一次快照后的数据 | 高 |
| **AOF** | Append Only File | 把每次**写命令**追加到日志文件（文本） | 高，最多丢 1 秒数据 | 中 |

> Redis 默认开启 **RDB**，AOF 默认关闭。两者可以同时开启，重启时 **AOF 优先**（数据更全）。

## 二、RDB 持久化

### 是什么

把某一时刻 Redis 的**全部内存数据**，以二进制格式**快照**保存到磁盘文件 `dump.rdb`。

```
内存中的数据 ──(快照)──▶ dump.rdb（二进制文件）
                           │
重启时 ──(加载快照)──▶ 内存恢复
```

### 触发方式

**① 手动触发**

```bash
# save：同步阻塞式，会阻塞主进程（生产禁用）
redis-cli save

# bgsave：异步后台执行，fork 子进程去写，不阻塞主服务（推荐）
redis-cli bgsave
```

**② 自动触发（配置 redis.conf）**

```conf
save 900 1        # 900 秒内至少有 1 次写操作 → 触发 bgsave
save 300 10       # 300 秒内至少有 10 次写操作 → 触发 bgsave
save 60 10000     # 60 秒内至少有 10000 次写操作 → 触发 bgsave
```

> 满足任一条件即触发，这三个规则是"时间 + 改动次数"的组合，用来平衡数据安全与性能。

### RDB 执行流程（bgsave）

```
① 主进程 fork 出一个子进程
② 子进程把内存数据写成 RDB 快照（写文件）
③ 写完后通知主进程，覆盖旧的 dump.rdb
```

- **fork**：复制一份主进程的内存页表（Copy-On-Write 写时复制）
- 子进程在写快照期间，主进程**继续对外服务**，不阻塞
- 写操作期间如果有数据变化，用的是 COW 机制，快照是"fork 那一刻"的

### 优缺点

| 优点 | 缺点 |
|------|------|
| 二进制紧凑，**恢复加载快** | 会**丢数据**：两次快照之间写的数据会丢 |
| 适合做**冷备份 / 数据迁移 / 灾备** | fork 有开销，大数据量时 fork 可能卡顿 |
| 文件体积小，适合传输 | 全量快照，不适合频繁执行 |

## 三、AOF 持久化

### 是什么

把每一次**写命令**（set / del / incr...）以明文文本**追加**到日志文件 `appendonly.aof`。

```
set name jack  ──▶ appendonly.aof
set age 20     ──▶ appendonly.aof
del name       ──▶ appendonly.aof   （每一条写操作都被记录）
```

重启时**重新执行**日志里的所有命令，就能还原数据。

### 开启与配置（redis.conf）

```conf
appendonly yes              # 开启 AOF
appendfilename "appendonly.aof"

# appendfsync：刷盘策略（每秒 vs 每次 vs 从不）
# always：每次写命令都刷盘（最安全，性能差）
# everysec：每秒刷一次盘（折中，最多丢 1 秒，默认）
# no：交给操作系统刷盘（性能好，可能丢更多）
appendfsync everysec
```

### 三种刷盘策略对比

| 策略 | 写命令后 | 可靠性 | 性能 |
|------|----------|--------|------|
| `always` | 立刻同步到磁盘 | 最多丢 1 条 | 差 |
| `everysec`（默认） | 每秒批量刷盘 | 最多丢 1 秒 | 中 |
| `no` | 交给 OS 决定 | 可能丢多秒 | 好 |

> 默认 `everysec`：性能与安全兼顾。

### AOF 重写（rewrite）

**为什么需要重写？** AOF 只增不改，日志文件会越来越大。比如 `set name a`、`set name b`、`set name c` 三条命令，其实只需要最后一条。

```conf
auto-aof-rewrite-percentage 100    # 文件膨胀到上次的 100% 时触发
auto-aof-rewrite-min-size 64mb     # 文件至少 64MB 才触发
```

**重写做什么：** 把当前内存数据整理成最精简的命令集，写入新的 AOF 文件，再替换旧文件。

```
旧 AOF：
  SET name a
  SET name b
  SET name c
  INCR count
  INCR count
重写后：
  SET name c
  SET count 2
```

> 重写过程由后台子进程完成（类似 bgsave），不阻塞主服务。

## 四、RDB vs AOF 总结

| 对比项 | RDB | AOF |
|--------|-----|-----|
| 数据格式 | 二进制快照 | 追加写命令（文本） |
| 数据完整性 | 可能丢两次快照间的数据 | everysec 最多丢 1 秒 |
| 文件体积 | 小、紧凑 | 大、且会膨胀（靠重写） |
| 恢复速度 | 快 | 慢（要重放所有命令） |
| 是否阻塞 | fork 有短暂开销 | 刷盘策略不同 |
| 默认 | 开启 | 关闭 |

**最佳实践：**
- **RDB + AOF 同时开启**，兼顾恢复速度和数据完整
- 重启时 Redis **优先加载 AOF**（数据更全）
- 冷备份 / 迁移用 RDB，实时高可靠用 AOF

## 五、小节

```
持久化小结：
  RDB ── 定期快照 ──▶ dump.rdb ──▶ 恢复快、会丢数据
  AOF ── 追加命令 ──▶ appendonly.aof ──▶ 恢复慢、最多丢1秒
  生产 ── 两者都开，AOF 优先加载
```
