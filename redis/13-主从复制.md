## 一、为什么需要主从复制

单机 Redis 有两大致命问题：

```
① 单点故障：Redis 挂了，整个服务不可用，数据也随着内存丢失
② 读写压力：所有读写都打到一台 Redis，性能瓶颈
```

**主从复制**（Replication）解决思路：一主多从。

```
             ┌──────────── 主节点 Master ────────────┐
             │  负责写操作（写命令同步给从节点）          │
             └─────────────────────────────────────┘
                        │ 数据复制（异步）
       ┌────────────────┼────────────────┐
       ▼                ▼                ▼
   ┌──────┐        ┌──────┐        ┌──────┐
   │ Slave│        │ Slave│        │ Slave│   从节点
   │  从   │        │  从   │        │  从   │   只负责读
   └──────┘        └──────┘        └──────┘
```

### 主从的作用

| 作用 | 说明 |
|------|------|
| **读写分离** | 主写从读，分摊读压力，提升并发读能力 |
| **数据冗余** | 主节点挂了，从节点还有完整数据副本 |
| **故障恢复基础** | 配合哨兵/集群可自动切换，是高可用的前提 |

## 二、主从架构的搭建

### 方式一：命令行（临时）

```bash
# 在从节点执行，指定主节点
redis-cli
> replicaof 192.168.1.10 6379    # 让当前节点成为该主的从
> replicaof no one               # 取消主从关系（变回独立节点）
```

### 方式二：配置文件（持久）

```conf
# 从节点的 redis.conf（或 redis-xxx.conf）
replicaof 192.168.1.10 6379      # 指定主节点 IP 和端口
replica-read-only yes            # 从节点只读（默认开）
```

### 配置示例：一主两从

```bash
# Master：6379（默认，什么都不配）
# Slave1：6380  redis.conf 加  replicaof 127.0.0.1 6379
# Slave2：6381  redis.conf 加  replicaof 127.0.0.1 6379
```

验证主从状态：

```bash
redis-cli -p 6379 info replication
# role:master                    ← 本机角色
# connected_slaves:2             ← 2 个从节点
# slave0:ip=... , state=online
```

## 三、主从数据同步原理（核心）

> 这里是我学到一半的重点：主从之间怎么把数据同步过去？

### 关键概念：replid 与 offset

| 概念 | 含义 |
|------|------|
| **replid** | 主节点的复制 ID，唯一标识一份"数据版本" |
| **offset** | 主从各自的复制偏移量，表示已经同步到哪条指令 |

```
每个 Redis 实例都维护：
  master_replid：数据集的版本标识
  master_repl_offset：主节点写命令的偏移量
  slave_repl_offset：从节点已同步的偏移量
```

> 判断主从数据是否一致：**replid 相同 且 offset 一致**。

---

### 全量同步

**触发时机：** 从节点刚连上主节点（第一次），或 replid 不一致（如主从重启过）。

```
Slave                          Master
  │  psync ? -1（第一次不知道 offset）   │
  │ ───────────────────────────────▶ │
  │                                 │  发送 replid + offset
  │ ◀─────────────────────────────── │  告诉从：我的版本和位置
  │  判断：replid 不一致 → 需要全量同步  │
  │                                 │
  │ ◀───────── 全量数据（RDB）──────── │  主节点 bgsave 生成 RDB 发过去
  │  保存 RDB，加载到内存              │
  │                                 │  并把同步期间的新写命令记录
  │ ◀────── 同步期间的增量命令 ──────── │  发给从节点补上
  │                                 │
  │ 之后：进入增量同步                 │
```

**流程：**
1. 从发 `psync ? -1`（不知道主的情况）
2. 主返回自己的 `replid` 和 `offset`
3. 从 replid 不一致 → 主执行 `bgsave`，生成 RDB 全量快照发给从
4. 从加载 RDB 恢复数据
5. 主在 bgsave 期间新产生的写命令，通过命令缓冲发给从，从补上
6. 同步完成，之后的写命令**实时增量同步**

---

### 增量同步

**触发时机：** 主从已建立连接、replid 一致，主节点每次写操作实时同步给从。

```
Master 执行写命令（如 set name jack）
          │
          ▼
  写入自己的 offset（master_repl_offset+1）
          │
          ▼
  把命令发给从节点
          │
          ▼
从节点执行命令，offset 追上主（slave_repl_offset+1）
```

> 主从 offset 一致 = 数据同步完成。从节点会定期向主报自己的 offset，主据此判断从有没有跟上。

---

### 全量 vs 增量，何时用哪个

| 同步类型 | 触发条件 | 数据量 | 特点 |
|----------|----------|--------|------|
| **全量同步** | 从首次连接 / replid 不一致 | 全部数据（RDB） | 慢、占带宽，只在初次/异常时用 |
| **增量同步** | 已连接且 replid 一致 | 只同步新增命令 | 快、实时，日常主力 |

> 记忆：**全量是"初次建立关系"或"版本对不上"才用，日常靠增量实时追。**

## 四、小结（已学部分）

```
主从复制：
  一主多从 ── 主写从读，读写分离，数据冗余
  全量同步 ── 初次连接 / replid 不一致 → 传 RDB
  增量同步 ── 已连接且 offset 追不上 → 实时传命令
  replid ── 数据版本标识 | offset ── 同步位置
```
