## 1. 统计需求：UV vs PV

### 1.1 概念区分

| 指标 | 全称 | 含义 | 去重 |
|------|------|------|------|
| **PV** | Page View（页面浏览量） | 用户每访问一次就 +1 | ❌ 不关注用户是谁 |
| **UV** | Unique Visitor（独立访客） | 同一个用户多次访问只算一次 | ✅ 必须去重 |

**示例：**
```
用户A访问了3次、用户B访问了2次、用户C访问了1次
PV = 6（共6次请求）
UV = 3（3个不同的用户）
```

### 1.2 传统去重方案的问题

| 方案 | 内存占用 | 精度 | 适用场景 |
|------|---------|------|---------|
| **HashSet** | O(n)，百万级 UV 内存爆炸 | 100% 精确 | 小数据量 |
| **Redis Set** | 同上，百万 IP 上百 MB | 100% 精确 | 中小数据量 |
| **MySQL COUNT(DISTINCT)** | 走磁盘，大表慢 | 100% 精确 | 离线统计 |
| **HyperLogLog** | 12KB，无论数据多大！ | 约 99.81% | **海量 UV 统计** |

## 2. HyperLogLog 数据结构

### 2.1 什么是 HyperLogLog？

HyperLogLog（HLL）是一种**概率性数据结构**，用于**基数统计**（统计不重复元素的数量）。

```
Redis 中 HyperLogLog 的特点：
- 固定内存：每个 key 仅占用 12KB
- 误差率：约 0.81%（标准误差）
- 可统计：最多 2^64 个不同元素
- 去重：自动去重，不需要手动维护
- 不存储元素本身：只知道"有多少种"，不知道"是哪些"
```

### 2.2 主要命令

```redis
# 添加元素（可批量）
PFADD key element [element ...]

# 统计基数（估算不重复元素数量）
PFCOUNT key [key ...]

# 合并多个 HLL
PFMERGE destkey sourcekey [sourcekey ...]
```

### 2.3 对比 Set 与 HyperLogLog

```redis
# Set 方案（精确，但占用内存大）
SADD uv:page:1001 user1 user2 user3
SCARD uv:page:1001    # → 3

# HyperLogLog 方案（近似，但 12KB 走天下）
PFADD uv:page:1001 user1 user2 user3
PFCOUNT uv:page:1001 # → 3（大概率）
```

## 3. UV 统计实现

### 3.1 数据结构设计

```
Key:   uv:{type}:{bizId}
Type:  HyperLogLog

示例：
uv:page:1001        → 页面 1001 的 UV
uv:shop:2001        → 店铺 2001 的 UV
uv:activity:3001    → 活动 3001 的 UV
```

### 3.2 每次访问记录 UV

```java
// 用户访问页面时，记录 UV
@GetMapping("/page/{pageId}")
public Result visitPage(@PathVariable Long pageId) {
    // 如果是登录用户，用 userId；未登录用 IP 或设备 ID
    String visitorId = Optional.ofNullable(UserHolder.getUser())
        .map(UserDTO::getId)
        .map(String::valueOf)
        .orElse(getClientIp());  // 备用方案

    // PFADD uv:page:{pageId} {visitorId}
    stringRedisTemplate.opsForHyperLogLog()
        .add("uv:page:" + pageId, visitorId);

    // ... 正常返回页面内容
}
```

### 3.3 查询 UV 数据

```java
// 统计今日全站 UV
@GetMapping("/uv/today")
public Result getTodayUV() {
    String date = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyyMMdd"));
    Long uv = stringRedisTemplate.opsForHyperLogLog()
        .size("uv:site:" + date);
    return Result.ok(uv);
}

// 统计某页面的累计 UV
@GetMapping("/uv/page/{pageId}")
public Result getPageUV(@PathVariable Long pageId) {
    Long uv = stringRedisTemplate.opsForHyperLogLog()
        .size("uv:page:" + pageId);
    return Result.ok(uv);
}
```

### 3.4 合并统计（周 / 月 UV）

```java
// 统计本周 UV（合并7天数据）
public Long getWeeklyUV() {
    LocalDate today = LocalDate.now();
    LocalDate monday = today.with(DayOfWeek.MONDAY);

    List<String> dailyKeys = new ArrayList<>();
    for (LocalDate date = monday; !date.isAfter(today); date = date.plusDays(1)) {
        dailyKeys.add("uv:site:" + date.format(DateTimeFormatter.ofPattern("yyyyMMdd")));
    }

    // PFMERGE 到临时 key 后统计
    String mergeKey = "uv:site:weekly:" + today.format(DateTimeFormatter.ofPattern("yyyyMMdd"));
    stringRedisTemplate.opsForHyperLogLog().union(mergeKey, dailyKeys.toArray(new String[0]));

    Long uv = stringRedisTemplate.opsForHyperLogLog().size(mergeKey);

    // 临时 key 设过期时间
    stringRedisTemplate.expire(mergeKey, 1, TimeUnit.HOURS);

    return uv;
}
```

## 4. HyperLogLog 原理简述

### 4.1 核心思想：伯努利试验

想象抛硬币：
```
抛硬币直到出现正面 → 记录抛的次数
第1次试验：反反反正 → 抛了4次，最大连续反面=3
第2次试验：反正     → 抛了2次，最大连续反面=1
第3次试验：正       → 抛了1次，最大连续反面=0
...

根据概率论：
- 抛一次硬币出现正面的概率 = 1/2
- 连续 k 次反面后再出现正面 ≈ 2^k 次试验才会有1次

所以：最大连续反面次数 = k → 大约进行了 2^k 次试验
```

### 4.2 映射到数据

```
元素 → Hash函数 → 二进制串 → 从低位看第一个1的位置（低位连续0的个数）

元素"user1001" → Hash → 1010|0001  ← 第一个1在第4位
元素"user1002" → Hash → 1100|1000  ← 第一个1在第4位  
元素"user1003" → Hash → 1110|0100  ← 第一个1在第3位

对最大 k 值取桶的平均 → 估算 UV ≈ 2^k

实际实现更复杂（16384个桶 + 取平均 + 偏差修正），使误差控制在 0.81%
```

### 4.3 为什么只要 12KB？

```
16384 个桶（2^14 个寄存器）
每个寄存器 6 bit（最多记录 2^6=64 次连续0，足够统计2^64个元素）
16384 × 6 bit = 98304 bit = 12 KB
```

## 5. HyperLogLog 的使用建议

| 场景 | 推荐 | 不推荐 |
|------|------|--------|
| 海量 UV 统计 | ✅ HyperLogLog（12KB，0.81% 误差） | ❌ Set（百万 UV 内存爆炸） |
| 需要精确到个位 | ❌ 误差 0.81% ≈ 百万级误差 8100 | ✅ Set（百万级几十 MB） |
| 需要知道具体是哪些用户 | ❌ 只存基数不存元素 | ✅ Set 或 MySQL |
| 日活 / 月活 / 周活 | ✅ HyperLogLog 合并极快 | ❌ 逐日存 Set 浪费内存 |
| 多个维度合并统计 | ✅ PFMERGE 一步搞定 | ❌ Set 做 UNION 慢 |

## 6. UV vs PV 统计的 Redis 方案对比

| 需求 | 数据结构 | 空间 | 精度 |
|------|---------|------|------|
| PV（每次+1） | String：`pv:{pageId}` | 极小 | 精确 |
| UV（按用户去重） | HyperLogLog：`uv:{pageId}` | 12KB | ~99.19% |
| 用户具体列表 | Set：`users:{pageId}` | O(n) | 精确 |
| 每日 UV | HLL：`uv:date:{yyyymmdd}` | 12KB/天 | 近似 |
| 每日用户明细 | Set：`uv_detail:{yyyymmdd}` | 大 | 精确 |

## 7. 关键知识点总结

| 内容 | 要点 |
|------|------|
| 数据结构 | HyperLogLog，概率性基数统计 |
| 内存 | 固定 12KB，与数据量无关 |
| 误差 | 标准误差约 0.81% |
| 核心命令 | PFADD / PFCOUNT / PFMERGE |
| 适用场景 | 海量 UV、DAU/MAU、不关心具体是谁只关心数量 |
| 不适用 | 需要精确值、需要知道具体元素 |
| 对比 Set | Set 精确但内存大，HLL 近似但内存极小 |
