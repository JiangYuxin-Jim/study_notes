# 12 - Redis 底层数据结构

> 📅 2026-07-29 | 🏷️ Redis / 数据结构 / SDS / ZipList / QuickList

---

## 1. 概述

Redis 之所以这么快，除了基于内存外，还得益于其**精巧的数据结构设计**。

```
5 种对外数据类型 → 底层使用 8 种内部编码

String  → SDS (Simple Dynamic String)
Hash    → ZipList / HashTable
List    → QuickList  (3.2+) / ZipList (旧)
Set     → IntSet / HashTable
ZSet    → ZipList / SkipList
```

Redis 会根据数据量和元素大小，在**不同编码之间自动转换**（编码升级）。

## 2. String 的底层 — SDS

### 2.1 为什么不用 C 语言的 char*？

C 语言字符串的问题：

```c
// C 语言字符串
char *s = "hello";
// 问题1：不记录长度，获取长度要遍历 O(n)
// 问题2：二进制不安全（遇到 '\0' 就认为是字符串结束）
// 问题3：修改字符串容易缓冲区溢出
// 问题4：修改需要重新分配内存
```

### 2.2 SDS 结构

```c
// Redis 3.2+ 的 SDS 结构（有多种类型：sdshdr5/8/16/32/64）
struct sdshdr {
    int len;        // 已使用长度
    int alloc;      // 分配的总长度（不包括头部和 null 终止符）
    unsigned char flags;  // 类型标志（区分 5/8/16/32/64 位）
    char buf[];     // 实际存储数据的字节数组
};
```

**SDS 的优势：**

| 特性 | C 字符串 | SDS |
|------|---------|-----|
| 获取长度 | O(n) | **O(1)** — 直接读 len 字段 |
| 二进制安全 | ❌ 不能含 '\0' | ✅ 以 len 为准，不是 '\0' |
| 缓冲区溢出 | ❌ 容易溢出 | ✅ 自动检查剩余空间，不足时扩容 |
| 预分配 | ❌ 每次修改都 realloc | ✅ 预分配额外空间（小于1MB翻倍，大于1MB+1MB） |
| 惰性空间释放 | ❌ | ✅ 缩短字符串时不释放内存，留待后用 |

### 2.3 SDS 的空间预分配策略

```
当修改后 SDS 长度 < 1MB → 分配 2×len + 1（1是终止符）
当修改后 SDS 长度 ≥ 1MB → 分配 len + 1MB + 1

示例：
"hello" → "hello world"（长度 11）
11 < 1MB → 实际分配：11×2+1 = 23 字节

"hello..."（1MB长）→ 追加1字节
≥ 1MB → 实际分配：1MB+1MB+1 = 2MB+1
```

## 3. ZipList（压缩列表）

### 3.1 什么是 ZipList

ZipList 是一种为了**节省内存**而设计的连续内存数据结构，用于存储小整数和短字符串。

```
内存布局（连续内存块）：
┌──────┬──────┬────────┬────────┬────────┬──────┐
│ zlbytes│ zltail│ zllen│ entry1│ entry2│ zlend│
│ 总字节 │ 尾偏移 │ 元素数 │  元素1  │  元素2  │ 255  │
├──────┴──────┴────────┴────────┴────────┴──────┤
│             连续内存区域                        │
└───────────────────────────────────────────────┘
```

### 3.2 Entry 结构

每个 entry 包含三部分：

```
┌─────────────┬────────────┬──────────┐
│ previous_length│ encoding   │ content   │
│ 前一entry长度  │ 编码类型    │ 实际数据   │
└─────────────┴────────────┴──────────┘
```

- **previous_entry_length**：前一个 entry 的长度（1 或 5 字节），用于**从后往前遍历**
- **encoding**：记录 content 的类型（整数/字符串）和长度
- **content**：实际数据

### 3.3 连锁更新问题

```
问题场景：
所有 entry 的 previous_length 都是 1 字节（前一个 entry <254字节）
突然插入一个 ≥254 字节的大 entry → 下一个 entry 的 previous_length 需要从 1→5 字节
→ 导致该 entry 体积增大 → 再下一个 entry 的 previous_length 也需要从 1→5 字节
→ 引发"多米诺骨牌"效应 → 连锁更新

实际影响：
- 128 个 entry 以内几乎无影响
- 连锁更新概率很低（需要连续多个临界大小的 entry）
- Redis 选择了"性能换空间"，实际使用中问题不大
```

### 3.4 ZipList 的使用场景

- Hash：元素数 < 512 且 value < 64 字节时使用（hash-max-ziplist-entries 和 hash-max-ziplist-value）
- List：在 Redis 3.2 之前使用
- ZSet：元素数 < 128 时使用

## 4. QuickList（快速列表）

### 4.1 为什么需要 QuickList

```
ZipList 的问题：
- 查询需要遍历 O(n)
- 连锁更新问题
- 过大时写入和删除效率低

双向链表（LinkedList）的问题：
- 每个节点需要 prev/next 指针（额外内存）
- 内存碎片化
- CPU 缓存不友好
```

**QuickList = ZipList + 双向链表的结合体**

```
┌──────────┐    ┌──────────┐    ┌──────────┐
│  节点1    │◄──►│  节点2    │◄──►│  节点3    │
│ ZipList  │    │ ZipList  │    │ ZipList  │
│ [e1,e2]  │    │ [e3,e4]  │    │ [e5]     │
└──────────┘    └──────────┘    └──────────┘
```

- 每个节点是一个 ZipList（限定大小）
- 节点之间通过双向链表连接
- 兼顾了**内存紧凑**和**操作灵活性**

### 4.2 QuickList 的配置

```redis
# redis.conf
list-max-ziplist-size -2      # -2 表示每个 zipList 最大 8KB
list-compress-depth 0         # 0 表示不压缩，可设为 1（压缩两端）
```

| 参数 | 说明 |
|------|------|
| list-max-ziplist-size | 正数=每个ZipList元素数上限，负数=文件大小（-1=4KB, -2=8KB...） |
| list-compress-depth | 0=不压缩，1=首尾各1个不压缩，其余压缩，2=首尾各2个不压缩 |

## 5. IntSet（整数集合）

### 5.1 什么是 IntSet

IntSet 是 Set 类型的一种内部编码，当集合中**全是整数**且**元素个数不多**时使用。

```c
typedef struct intset {
    uint32_t encoding;  // 编码方式（INTSET_ENC_INT16 / INT32 / INT64）
    uint32_t length;    // 元素个数
    int8_t contents[];  // 实际存储数组（按 encoding 解析）
};
```

### 5.2 升级机制

```c
// 初始：IntSet 用 int16 编码（每个元素2字节）
// 存入 1, 2, 3 → 全是 int16 范围
// 存入 65536 → 超出 int16 范围 → 升级到 int32

// 升级过程：
// 1. 扩大数组长度（按新编码）
// 2. 将旧元素按新编码重写
// 3. 存入新元素

// 特性：
// - 升级不可逆（不会有"降级"）
// - 节省内存（尽量用小编码）
```

### 5.3 配置

```redis
set-max-intset-entries 512    # 元素超过 512 或包含非整数 → 转为 HashTable
```

## 6. SkipList（跳表）

### 6.1 为什么需要 SkipList

ZSet 需要同时支持：
1. **快速查询单个元素** → 需要 Hash 或类似结构
2. **按 score 范围查询** → 需要有序结构

```
平衡树：范围查询 O(log n)，但实现复杂
B+树：InnoDB 使用，适合磁盘场景
SkipList：实现简单，范围查询友好，Redis 使用
```

### 6.2 SkipList 结构

```
level 3  ────────► 30 ──────────────►  nil
level 2  10 ──────► 30 ──────► 50 ──►  nil  
level 1  10 ──► 20──► 30 ──► 40──► 50──► nil
level 0  10─►15─►20─►25─►30─►35─►40─►45─►50─► nil

查找 45 的路径（从上往下）：
30 → 50（大于45）→ 回到30 → 40 → 50（大于45）→ 回到40 → 45 ✅
```

**核心思想**：以"概率"的方式构建多层索引，上层是下层的"快速通道"。

### 6.3 SkipList vs 平衡树

| 特性 | SkipList | 平衡树（AVL/红黑树） |
|------|----------|-------------------|
| 实现复杂度 | 简单（约30行伪代码） | 复杂（旋转平衡） |
| 查询复杂度 | O(log n) 期望 | O(log n) 严格 |
| 范围查询 | 只需一次找到起点，向后遍历 | 需要中序遍历 |
| 插入/删除 | 无需 rebalance | 需要 rebalance |
| 内存效率 | 较低（每节点多层指针） | 较高 |
| 锁友好 | 分段加锁容易 | 结构精细，难分段 |

### 6.4 ZSet 的内部结构

```c
typedef struct zset {
    dict *dict;         // 字典：member → score（用于快速查单个元素的 score）
    zskiplist *zsl;     // 跳表：score → member（用于范围查询和排序）
};
```

所以 ZSet 实际上是一个 **dict + skipList 的组合结构**：
- dict：O(1) 查询某个元素的 score
- skipList：O(log n) 范围查询和 TOP N 查询

**内存开销**：每个元素存两份（dict 和 skipList），用内存换功能。

## 7. 数据类型与底层编码对照表

| 键类型 | 底层编码 | 触发条件 |
|--------|---------|---------|
| String | int | 纯整数，可以用 long 表示 |
| String | embstr | 字符串长度 ≤ 44 字节 |
| String | raw | 字符串长度 > 44 字节 |
| Hash | ZipList | 元素 ≤ 512 个且 value ≤ 64 字节 |
| Hash | HashTable | 超过 ziplist 限制 |
| List | QuickList | 始终使用（3.2+） |
| Set | IntSet | 全是整数且元素 ≤ 512 个 |
| Set | HashTable | 超过 IntSet 限制 |
| ZSet | ZipList | 元素 ≤ 128 个且 value ≤ 64 字节 |
| ZSet | SkipList | 超过 ziplist 限制 |

## 8. 关键知识点总结

| 结构 | 特点 |
|------|------|
| SDS | 动态字符串，O(1)长度，二进制安全，预分配 |
| ZipList | 连续内存，紧凑存储，连锁更新问题 |
| QuickList | ZipList + 双向链表，平衡内存和操作 |
| IntSet | 整数集合，自动升级编码 |
| SkipList | 多层索引链表，O(log n) 范围查询 |
| ZSet | dict + skipList 组合，效率与功能兼得 |
