## 1. Redis 为什么这么快

```
1. 基于内存 —— 数据全在内存中（微秒级读写）
2. IO 多路复用 —— 单线程处理大量并发连接
3. 数据结构高效 —— SDS/跳表/压缩列表等精巧设计
4. 避免上下文切换 —— 单线程模型没有锁竞争
5. Reactor 设计模式 —— 事件驱动架构
```

## 2. Redis 的 IO 模型演变

### 2.1 传统 BIO（阻塞 IO）

```java
// 传统 Socket 编程
ServerSocket server = new ServerSocket(6379);

while (true) {
    Socket client = server.accept();     // ⚠️ 阻塞等待客户端连接
    InputStream in = client.getInputStream();
    
    byte[] buf = new byte[1024];
    in.read(buf);                        // ⚠️ 阻塞等待数据到达
    
    // 处理...（必须等前一个连接处理完才能处理下一个）
}
```

**BIO 的问题**：一个线程只能处理一个连接 → 大量连接时需要大量线程 → 线程切换开销巨大。

### 2.2 IO 多路复用

IO 多路复用允许**一个线程同时监听多个 Socket 连接**：

```
传统方式（BIO）：
线程1 ── socket1 ── （阻塞等待）
线程2 ── socket2 ── （阻塞等待）
线程3 ── socket3 ── （阻塞等待）
        ...（线程数 = 连接数）

IO 多路复用：
线程 ── [select/epoll] ── socket1（就绪通知）
                        ├── socket2（就绪通知）
                        ├── socket3（就绪通知）
                        └── socketN（就绪通知）
        一个线程监听所有连接
```

### 2.3 select / poll / epoll

| 模型 | 复杂度 | 最大连接数 | 工作方式 |
|------|--------|-----------|---------|
| select | O(n) | 1024（有限制） | 轮询所有 fd，每次调用需从用户态拷贝 fd_set 到内核态 |
| poll | O(n) | 无限制 | 同 select，但用链表代替 fd_set，无上限 |
| epoll | O(1) | 无限制 | **事件驱动**，只返回就绪的 fd，无需轮询 |

**epoll 的核心三个 API：**

```c
// 1. 创建 epoll 实例
int epfd = epoll_create(1024);

// 2. 注册要监听的文件描述符和事件
struct epoll_event ev;
ev.events = EPOLLIN;     // 监听可读事件
ev.data.fd = socket_fd;
epoll_ctl(epfd, EPOLL_CTL_ADD, socket_fd, &ev);

// 3. 等待事件发生（只返回就绪的连接）
int ready_count = epoll_wait(epfd, events, MAX_EVENTS, -1);
for (int i = 0; i < ready_count; i++) {
    // 处理 events[i].data.fd 上的事件
}
```

**epoll 的优点：**
- 只返回就绪的 fd → 不需要遍历所有连接（O(1)）
- 就绪 fd 存于内核**事件表** → 无需每次从用户态拷贝
- 水平触发（LT）和边缘触发（ET）两种模式

## 3. Redis 的 Reactor 模式

### 3.1 Reactor 设计模式

Reactor 是一种事件驱动设计模式，将**事件分发**和**事件处理**分离：

```
┌───────────────────────────────┐
│          Reactor              │
│  (事件循环 / 事件分发器)        │
└──────┬─────────────────┬──────┘
       │                 │
       ▼                 ▼
  ┌────────┐       ┌────────┐
  │ Handler1│       │ Handler2│
  │ 读事件  │       │ 读事件  │
  └────────┘       └────────┘
```

### 3.2 Redis 的 Reactor 实现

Redis 的 aeEventLoop 就是一个 Reactor：

```
aeEventLoop（核心事件循环）
    │
    ├── 文件事件（File Event）
    │       ├── Socket 可读事件 → 读客户端请求
    │       ├── Socket 可写事件 → 写响应给客户端
    │       └── 监听 Socket → accept 新连接
    │
    └── 时间事件（Time Event）
            ├── 定时执行 serverCron（更新统计信息/清理过期key等）
            └── 其他定时任务
```

**Redis 事件循环伪代码：**

```python
def aeMain():
    while True:
        # 1. 用 epoll 等待事件（阻塞直到有事件到达）
        events = aeApiPoll(tv)
        
        # 2. 处理文件事件（有先后顺序）
        for event in events:
            if event.type == AE_READABLE:
                # 读 → 解析命令 → 执行命令 → 将结果写入写缓冲区
                readQueryFromClient(event.client)
            elif event.type == AE_WRITABLE:
                # 将缓冲区的响应数据发回客户端
                sendReplyToClient(event.client)
        
        # 3. 处理时间事件（如定时反弹过期 key）
        processTimeEvents()
```

### 3.3 Redis 6.0 的多线程 IO

```
Redis 6.0 之前的 IO 模型：
主线程 ── [epoll] ── 读数据 ── 解析 ── 执行命令 ── 写回
（所有步骤都是单线程）

Redis 6.0+ 引入 IO 多线程：
主线程 ── [epoll] ── 等待事件
                      │
            ┌─────────┼─────────┐
            │         │         │
         IO线程1    IO线程2   IO线程3
         (读/写)    (读/写)   (读/写)
            │         │         │
            └─────────┼─────────┘
                      │
                  主线程 ──── 执行命令（仍单线程）
```

**重要说明：**
- **命令执行仍然是单线程的** — 不需要考虑并发问题
- 只有 **网络 IO（读请求/写响应）** 使用多线程并行处理
- 默认不开启（`io-threads 4` 配置开启）
- 读和写各有一个线程池

## 4. RESP 协议

### 4.1 什么是 RESP

RESP（REdis Serialization Protocol）是 Redis 客户端与服务器之间的**通信协议**，是一种**文本协议**。

```markdown
特点：
- 简单：人类可读
- 高效：不需要复杂的解析
- 二进制安全：以长度确定字符串边界
- 支持多种数据类型
```

### 4.2 RESP 协议格式

RESP 协议中，每个消息由**第一个字节**确定类型：

| 第一个字节 | 类型 | 格式 | 示例 |
|-----------|------|------|------|
| `+` | 简单字符串 | `+OK\r\n` | 命令执行成功 |
| `-` | 错误 | `-ERR syntax error\r\n` | 错误信息 |
| `:` | 整数 | `:1\r\n` | 整数值 |
| `$` | 批量字符串 | `$5\r\nhello\r\n` | 长度+内容 |
| `*` | 数组 | `*2\r\n$3\r\nGET\r\n$3\r\nkey\r\n` | 多个元素的数组 |

### 4.3 举例：客户端发送命令

```redis
# 客户端发送：SET name zhangsan

# 实际传输的 RESP 协议内容：
*3\r\n                         ← 数组，3个元素
$3\r\n                         ← 元素1："SET"（长度3）
SET\r\n
$4\r\n                         ← 元素2："name"（长度4）
name\r\n
$8\r\n                         ← 元素3："zhangsan"（长度8）
zhangsan\r\n

# 服务器响应：
+OK\r\n                        ← 简单字符串 OK
```

### 4.4 内联命令

Redis 也支持简单的空格分隔格式（仅用于简单命令）：

```redis
SET name zhangsan
# 内部也会转为 RESP 格式处理
```

## 5. Redis 的线程模型

### 5.1 命令执行是单线程的

```markdown
Redis 的单线程指的是：**命令的执行在单个线程中串行执行**

单线程的优势：
1. 无锁竞争 —— 不需要锁，不会死锁
2. 无上下文切换 —— CPU 缓存友好
3. 实现简单 —— 不用担心并发问题

单线程的瓶颈：
1. CPU 不是瓶颈（内存才是）
2. 单条命令不能太慢（KEYS * 等 O(n) 命令阻塞其他命令）
```

### 5.2 哪些环节不是单线程的

```
非单线程的操作：
1. BGSAVE —— fork 子进程做 RDB
2. AOF 重写 —— fork 子进程
3. 异步删除 —— UNLINK / FLUSHDB ASYNC（另起线程处理）
4. 集群同步 —— 用单独的线程处理主从复制
5. IO 多线程（6.0+）—— 读写 IO 用多线程并行
```

## 6. 关键知识点总结

| 内容 | 要点 |
|------|------|
| IO 模型 | IO 多路复用（epoll），单线程处理所有连接 |
| Reactor 模式 | 事件循环，文件事件+时间事件 |
| 6.0 多线程 | IO 读写多线程，命令执行仍单线程 |
| RESP 协议 | `+/-/:/$/*` 五种前缀，文本协议，二进制安全 |
| 单线程优势 | 无锁、无切换、实现简单 |
| 性能瓶颈 | 慢命令导致阻塞（KEYS、大数据集 DEL、复杂 Lua） |
