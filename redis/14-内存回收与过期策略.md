## 1. Redis 的过期策略

### 1.1 设置过期时间

```redis
# 设置过期时间的 4 种方式
EXPIRE key seconds           # 设置 key 在 seconds 秒后过期
PEXPIRE key milliseconds     # 毫秒级过期
EXPIREAT key timestamp       # 在指定时间戳（秒）过期
PEXPIREAT key milliseconds   # 在指定时间戳（毫秒）过期

# 注意：SETEX 也设置过期，是 SET + EXPIRE 的原子版本

# 查看剩余存活时间
TTL key                      # 返回剩余秒数，-1 永不过期，-2 已过期不存在
PTTL key                     # 毫秒级
```

### 1.2 三种过期删除策略

| 策略 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **定时删除** | 设置过期时创建定时器，到期立即删除 | 内存最友好，立即释放 | CPU 不友好，大量过期 key 需大量定时器 |
| **惰性删除** | 访问时才检查是否过期 | CPU 友好 | 内存不友好（过期 key 不访问就不删除） |
| **定期删除** | 每隔一段时间扫描一部分 key | 折中 | 难以确定合理的执行频率 |

### 1.3 Redis 的组合策略：惰性删除 + 定期删除

```
访问时（惰性删除）：
key 到期了 ── 用户查询 ── 发现已过期 ── 删除 ── 返回 nil

定期扫描（定期删除）：
每 100ms 执行一次：
1. 从所有设置了过期时间的 key 中随机选 20 个
2. 删除其中已过期的 key
3. 如果删除比例 > 25%，重复步骤 1-2
4. 本轮最多执行 16ms（防止 CPU 耗时过长）
```

**为什么不用定时删除？**
```
100 万个 key 过期 → 创建 100 万个定时器 → 定时器管理本身就是巨大开销
定时删除在理论上是完美的，但现实不可行
```

**为什么要有定期删除？**
```
惰性删除的问题：
一条热点新闻过期了 → 但永远没人查这条缓存 → 这条 key 就一直占着内存
定期删除保证了"至少会扫描到"这些冷数据
```

## 2. Redis 的内存淘汰策略

### 2.1 什么时候触发淘汰

```
当 Redis 的已用内存达到 maxmemory 限制时，开始选择键淘汰
（不是满了才淘汰，而是写入时会检查并淘汰）
```

```redis
# redis.conf
maxmemory 1gb                        # 最大内存 1GB
maxmemory-policy volatile-lru        # 淘汰策略（默认 noeviction）
maxmemory-samples 5                  # LRU/LFU/TTL 算法采样数量（默认5）
```

### 2.2 八种淘汰策略

| 策略 | 含义 | 适用场景 |
|------|------|---------|
| **noeviction** | 不淘汰，写满就报错 | 不常用于缓存（适合做数据库） |
| **volatile-lru** | 对有过期时间的 key 做 LRU | 最常用，缓存业务首选 |
| **allkeys-lru** | 对所有 key 做 LRU | 缓存通用场景 |
| **volatile-lfu** | 对有过期时间的 key 做 LFU（4.0+） | 需要根据访问频率淘汰 |
| **allkeys-lfu** | 对所有 key 做 LFU（4.0+） | 冷热数据差异大的场景 |
| **volatile-ttl** | 优先淘汰剩余 TTL 最小的 key | 特定场景 |
| **volatile-random** | 对有过期时间的 key 随机淘汰 | 不常用 |
| **allkeys-random** | 对所有 key 随机淘汰 | 极少数场景 |

### 2.3 如何选择淘汰策略

```markdown
1. 大多数缓存场景 → volatile-lru
   - 设置过期时间的 key 作为缓存
   - 永不过期的 key 作为业务数据

2. 只做缓存（所有 key 都有 TTL）→ allkeys-lru
   - 简单粗暴

3. 热点数据差异大 → allkeys-lfu
   - 有些 key 经常访问，有些几乎不访问
   - LFU 能更好保留"长期热门"的数据

4. 数据库场景（不能丢数据）→ noeviction
   - 写满时不再写入，保证已有数据不丢
```

## 3. LRU 算法（Least Recently Used）

### 3.1 标准的 LRU

```
最近最久未使用：
淘汰最长时间没被访问的数据

操作：
访问 key1 → 移到链表头部
访问 key2 → 移到链表头部
访问 key3 → 移到链表头部
...链表满了...
                     ← 淘汰链表尾部的 key
```

**标准 LRU 的问题**：维护一个全局有序链表，每次访问都要调整位置，内存开销大。

### 3.2 Redis 的近似 LRU

Redis 没有实现标准的 LRU，而是使用**近似 LRU**算法：

```
淘汰过程：
1. 从 Redis 的 key 空间中随机采样（maxmemory-samples 个 key）
2. 淘汰其中 idle time（空闲时间）最大的 key
3. 如果不够，重复采样淘汰

采样数越大，越接近真正的 LRU（性能越差）
默认采样数 = 5，是内存和准确度的折中
```

**近似 LRU vs 标准 LRU：**

```
标准 LRU 能完美淘汰"最久未使用"的数据
近似 LRU 只能淘汰"采样中空闲最久"的数据

但实践中：
- 近似 LRU 的效果已经非常接近标准 LRU
- 采样数提高到 10，准确性提升到约 95%
- 不需要维护全局有序链表，内存省很多
```

## 4. LFU 算法（Least Frequently Used）

### 4.1 为什么需要 LFU

```
LRU 的问题：
一个 key 被大量访问 → 暂存到缓存 → 之后不再访问 → 但它在链表头部
另一个 key 最近被频繁访问 → 但刚好在它之后被大量访问了一次 → 反而被淘汰了

LRU 只看"最近一次访问时间"，不看"历史访问频率"
LFU 考虑了"访问频率"，更适合有稳定热度的场景
```

### 4.2 LFU 的实现

Redis 4.0+ 支持 LFU 淘汰策略，通过**访问计数 + 衰减机制**实现：

```c
// 每个 key 的 lru 字段在 LFU 模式下被拆成两部分：
// 高 16 位：最后递减时间（last decrement time）→ 单位分钟
// 低 8 位：访问计数（counter）→ 最大值 255

// 计数增长（访问时）：
// 计数越大，增长越慢（对数增长）
counter = LFULogIncr(counter);
// 约等于：counter = min(255, counter + random_based_on(counter))

// 计数衰减（定期）：
// 每隔 N 分钟，counter 减半
// N 由 lfu-decay-time 配置
// lfu-decay-time = 1 → 每分钟衰减一次
```

**为什么计数越大增长越慢？**

```
这是为了避免高频 key 霸占最大计数：
- counter=0 → 每次访问 +1 概率 ≈ 100%
- counter=10 → 每次访问 +1 概率 ≈ 50%
- counter=100 → 每次访问 +1 概率 ≈ 10%
- counter=255 → 不再增长

这样：短期高频 vs 长期高频都能合理体现
```

### 4.3 LFU 配置

```redis
# redis.conf
maxmemory-policy allkeys-lfu        # 开启 LFU 淘汰
lfu-log-factor 10                    # 计数器增长因子（越大越难增长）
lfu-decay-time 1                     # 衰减时间（分钟）
```

## 5. 内存碎片

### 5.1 碎片产生的原因

```
1. 内存分配器（jemalloc/tcmalloc）分配时按固定大小分配
   - 需要 10 字节 → 实际分配 16 字节 → 6 字节碎片

2. 频繁的修改和删除
   - String append 导致 realloc → 旧内存碎片
   - 大 key 删除后留下空洞

3. 不同大小的数据交替存储
   - 分配了大块内存 → 释放 → 又申请小块 → 碎片化
```

### 5.2 查看和清理碎片

```redis
# 查看内存信息
INFO memory

# 关注指标
used_memory: 1024000              # 实际使用内存（数据）
used_memory_rss: 2048000           # 向 OS 申请的内存（包含碎片）
mem_fragmentation_ratio: 2.0       # 碎片率 = used_memory_rss / used_memory

# 碎片率判断
# 1.0 - 1.5：正常
# > 1.5：碎片较多，需要清理
# < 1.0：内存不足，操作系统在 swap（危险！）
```

**清理碎片（Redis 4.0+）：**

```redis
# 手动触发碎片整理
MEMORY PURGE

# 自动碎片整理（通过配置）
activedefrag yes                   # 开启自动碎片整理
active-defrag-threshold-lower 10    # 碎片率超过 10% 开始整理
active-defrag-threshold-upper 100   # 碎片率超过 100% 全力整理
active-defrag-cycle-min 5           # CPU 使用下限（5%）
active-defrag-cycle-max 75          # CPU 使用上限（75%）
```

## 6. Redis 为什么用 jemalloc

Redis 默认使用 **jemalloc**（Facebook 开发的内存分配器），主要优势：

| 特性 | jemalloc | glibc malloc |
|------|----------|-------------|
| 多线程 | 优秀（线程缓存） | 一般（锁竞争） |
| 碎片控制 | 分桶管理，碎片少 | 碎片容易积累 |
| 大页支持 | 支持透明大页 | 部分支持 |
| 内存局部分 | 好（CPU 缓存友好） | 一般 |

**jemalloc 的分桶策略：**
```
大小类：8, 16, 32, 48, 64, 80, 96, 112, 128, ...
       160, 192, 224, 256, 320, 384, 448, 512, ...
       640, 768, 896, 1024, 1280, 1536, 1792, 2048, ...

小数据（字符串 < 8 字节）→ 也占 8 字节 bucket
大数据（字符串 1KB）→ 分配近似大小的 bucket
```

## 7. 关键知识点总结

| 内容 | 要点 |
|------|------|
| 过期策略 | **惰性删除**（访问时删）+ **定期删除**（每100ms随机扫20个） |
| 淘汰策略 | 8 种策略，**volatile-lru** 最常用 |
| LRU | 近似 LRU，采样 5 个 key 淘汰最久未用的 |
| LFU | 对数增长 + 定期衰减，适合热度稳定的场景 |
| 碎片 | jemalloc 分配器，`MEMORY PURGE` 整理，自动碎片整理 |
| 淘汰触发时机 | 写入操作达到 maxmemory 时触发 |
