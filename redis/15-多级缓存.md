# 15 - Redis 多级缓存（Caffeine + OpenResty + Canal）

> 📅 2026-08-04 | 🏷️ Redis / 高级篇 / 多级缓存 / Nginx / 缓存同步

## 一、什么是多级缓存

**背景**：传统 Redis 缓存（Redis 作为独立缓存，Tomcat 直连）存在两个痛点：
1. 请求要经过 **Tomcat**，Tomcat 的并发能力成为瓶颈（线程池有限）。
2. Redis 是**网络访问**（跨进程），比 JVM 内存访问慢一个量级。

**多级缓存思路**：把缓存"下沉"到离用户更近的每一层，逐级兜底，只有最靠近数据的层级才真正打到后端。

```
浏览器
  ↓ (1) 浏览器缓存（本地）
Nginx（OpenResty）
  ↓ (2) Nginx 本地缓存（Lua Shared Dict）—— 最快，毫秒级
Redis
  ↓ (3) Redis 缓存
Tomcat（JVM 进程内缓存 Caffeine）
  ↓ (4) 进程内缓存
数据库 MySQL
```

**多级缓存架构的核心流程（以查询商品为例）**：
1. 请求先到 **Nginx/OpenResty**，若本地缓存命中直接返回（最快的 1 级）。
2. 未命中 → 查 **Redis**，命中直接返回。
3. 未命中 → 发 HTTP 请求给 **Tomcat**，Tomcat 先从 **Caffeine 进程内缓存**查。
4. 进程缓存未命中 → 查**数据库**，然后**回填**：数据库 → Caffeine 进程缓存 → Redis → Nginx 本地缓存。
5. 每一级缓存都要设置**淘汰策略**和**过期时间**，避免数据堆积。

> 与传统单级 Redis 缓存相比，多级缓存把热点数据放到了**进程内存**和 **Nginx 内存**里，访问路径更短、性能更高，能扛住超大并发（如秒杀抢购场景）。

## 二、JVM 进程缓存（Caffeine）

### 1. Demo 工程与数据导入

- 多级缓存 Demo 使用 **商品（item）+ 商品库存（stock）** 两个表，作为演示数据。
- 导入 Demo 数据后，商品信息通过 JVM 进程缓存承载高频查询。

### 2. 初识 Caffeine

Caffeine 是**基于 Java 8 的高性能本地缓存库**，Google Guava Cache 的升级版，被 Spring 官方推荐。

**核心 API 演示**：

```java
// 手动创建缓存：数量上限 + 过期策略
Cache<String, String> cache = Caffeine.newBuilder()
        .maximumSize(1_000)              // 最大容量
        .expireAfterWrite(Duration.ofSeconds(10))  // 写入后 10 秒过期
        .build();

// 写入
cache.put("key1", "value1");
// 查询（未命中返回 null）
String v = cache.getIfPresent("key1");

// get(key, mappingFunction)：未命中时用函数加载并回填（类似 Redis 的缓存回填）
String v2 = cache.get("key2", k -> db.query(k));
```

**Caffeine 特点**：
- **内存级**操作，无网络开销，纳秒级响应。
- 数据存于 JVM 堆内，进程重启即丢失（适合热点数据，不适合必须具备持久性的数据）。
- 支持**容量限制（maximumSize / maximumWeight）**与**淘汰策略**：`expireAfterWrite`（写后过期）、`expireAfterAccess`（访问后过期）、`refreshAfterWrite`（写后定时刷新）。

### 3. 在 Spring 中实现进程缓存

Spring 对 Caffeine 做了封装，通过 `@Cacheable` 注解即可使用：

```yml
# application.yml 配置 Caffeine 作为缓存
spring:
  cache:
    type: caffeine
    caffeine:
      spec: maximumSize=10000,expireAfterWrite=300s
```

```java
@Service
public class ItemService {
    @Cacheable(value = "item", key = "#id")
    public Item queryById(Long id) {
        return itemMapper.selectById(id); // 未命中才执行，结果自动缓存
    }
}
```

- `@Cacheable`：先查缓存，命中直接返回；未命中执行方法并**自动把结果写入缓存**。
- 缓存名（`value`）与 key 组合成最终的缓存键。
- 配合 Caffeine 的容量/过期配置，实现 JVM 级进程缓存。

## 三、多级缓存核心：OpenResty（Lua + Nginx）

### 1. Lua 语法初识

OpenResty 内嵌 **Lua**（轻量脚本语言）来扩展 Nginx。Lua 基础语法：

```lua
-- 注释
local a = 10            -- 变量（local 局部变量）
local s = "hello"       -- 字符串
local b = true          -- 布尔

-- 变量和循环
for i = 1, 10 do
    print(i)
end

while a > 0 do
    a = a - 1
end

-- 函数
local function add(x, y)
    return x + y
end

-- 条件控制
if x > 0 then
    print("positive")
elseif x < 0 then
    print("negative")
else
    print("zero")
end
```

**Lua 要点**：
- 索引**从 1 开始**（不是 0）。
- 变量默认全局，用 `local` 声明为局部变量（推荐，避免污染）。
- 函数用 `function ... end`，支持 return 多返回值。

### 2. 安装 OpenResty

OpenResty = **Nginx + Lua**（高性能 Web 平台）。安装后配置文件位于 `/usr/local/openresty/nginx/conf/nginx.conf`。

### 3. OpenResty 快速入门

在 `nginx.conf` 的 server 块中，用 `content_by_lua_block` 直接执行 Lua：

```nginx
location /lua {
    default_type 'text/html';
    content_by_lua_block {
        ngx.say('<h1>Hello, Lua</h1>')   -- 输出到响应
    }
}
```

- `ngx.say()`：输出响应内容。
- `ngx.log()`：打印日志。
- 通过 Lua 处理请求逻辑，可做**读取参数、发 HTTP 请求、读写缓存**等。

### 4. 获取请求参数

在 OpenResty 中取地址栏参数：

```nginx
location /item/{id} {
    content_by_lua_block {
        local id = ngx.var.uri:match("/item/(%d+)")   -- 从 URI 正则提取商品 id
        ngx.say("id = " .. id)
    }
}
```

或取 query 参数：

```lua
local action = ngx.var.arg_action   -- ?action=xxx
```

### 5. 封装 Http 请求工具（发请求给后端）

用 **`resty.http`** 库在 Lua 里发起 HTTP 请求（OpenResty 访问 Tomcat 的桥梁）：

```lua
-- 引入 http 模块
local http = require "resty.http"
local httpc = http.new()

-- 发起 GET 请求到 Tomcat
local resp, err = httpc:request_uri("http://localhost:8081/item/1001", {
    method = "GET",
    keepalive_timeout = 60,
    keepalive_pool = 10
})

-- 获取响应体
local body = resp.body
ngx.say(body)
```

- 复用连接池（`keepalive`）可显著提升性能，避免频繁建立连接。
- 这是多级缓存里 **OpenResty → Tomcat** 的关键一跳。

### 6. 向 Tomcat 发请求（含根据商品 id 做负载均衡）

OpenResty 会访问**多个 Tomcat**（集群），需要**按商品 id 负载均衡**（哈希路由，保证同一商品始终访问同一台 Tomcat，从而命中该 Tomcat 的 JVM 进程缓存）：

```nginx
upstream tomcat-cluster {
    hash $request_uri;        # 按请求 URI 哈希负载均衡
    server 192.168.150.101:8081;
    server 192.168.150.102:8081;
}
```

```lua
-- 动态选择后端 host（根据商品 id 哈希到固定节点，便于命中 JVM 缓存）
local backend = balance.item(id)   -- 自定义哈希策略
local resp = httpc:request_uri("http://" .. backend .. "/item/" .. id, { method = "GET" })
```

> **为什么要按商品 id 哈希**：多级缓存中，JVM 进程缓存（Caffeine）只在单台 Tomcat 内存里。若随机负载均衡，同一商品会打散到不同 Tomcat，进程缓存永远命中不了。**哈希路由让同一商品固定打到同一台 Tomcat**，才能发挥 JVM 进程缓存的作用。

### 7. Redis 缓存预热 + 查询 Redis

**缓存预热**：服务启动时，把数据库中的热点数据提前写入 Redis，避免上线瞬间大量请求穿透到数据库。

```nginx
location /preheat {
    content_by_lua_block {
        -- 从数据库/文件读取商品数据，批量写入 Redis
        -- 使用 resty.redis 连接 Redis set 进去
    }
}
```

**查询 Redis**（Nginx → Redis）：

```lua
local redis = require "resty.redis"
local red = redis:new()

red:set_timeouts(1000, 1000, 1000)   -- 连接/读写超时
local ok, err = red:connect("127.0.0.1", 6379)

-- 缓存 key 约定：item:1001
local cacheKey = "item:" .. id
local val = red:get(cacheKey)

if val == ngx.null or val == nil then
    -- Redis 未命中，发起 HTTP 请求到 Tomcat 查询
else
    -- 命中，直接返回（注意序列化/反序列化）
end
```

### 8. Nginx 本地缓存（OpenResty 的 lua_shared_dict）

在 Nginx 内存中开辟一块**共享缓存字典**（多 worker 进程共享），作为**第 1 级**最快速的缓存：

```nginx
# 声明共享内存缓存区，大小 10m
lua_shared_dict item_cache 10m;
```

```lua
local cache = ngx.shared.item_cache

-- 尝试读本地缓存
local val = cache:get("item:" .. id)
if not val then
    -- 未命中：查 Redis → 仍未命中查 Tomcat → 回填写入本地缓存
    cache:set("item:" .. id, value, 600)   -- 600 秒过期
end
```

> **多级缓存完整链路（一次商品查询）**：
> 1. `lua_shared_dict` Nginx 本地缓存 → 命中返回 ✓（最快）
> 2. Redis → 命中返回，并回填 Nginx 本地缓存
> 3. Tomcat：先从 Caffeine 进程缓存查 → 未命中查 DB → 回填 Caffeine + Redis + Nginx
> 4. 通过 **缓存预热** 提前把热点数据放进各级缓存，减少冷启动穿透。

## 四、缓存同步（Canal）

### 1. 数据同步策略

多级缓存面临的核心难题：**数据库数据一旦更新，所有层级的缓存如何保持一致？**

常见策略对比：

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **设置有效期** | 缓存过期后重新加载 | 简单 | 存在短暂不一致窗口 |
| **同步双写** | 业务代码里同时更新 DB + 删缓存 | 直接 | 与业务耦合，易漏 |
| **异步通知（Canal）** | DB 变更 → 订阅 binlog → 主动删缓存 | 解耦、可靠 | 需要额外中间件 |

> 主流方案：**Canal 监听 MySQL binlog**，数据库一变更就异步通知各层清除/更新缓存，保证一致性。

### 2. 安装 Canal

Canal 是阿里开源的 **MySQL binlog 订阅组件**，伪装成 MySQL 从库，实时解析 binlog 变更。

```
MySQL (binlog)  →  Canal  → 消息（变更事件） → 业务系统（消费，更新/删除缓存）
```

- Canal 通过 **`canal-server`** 连接 MySQL，读取 binlog。
- 业务侧用 **`canal-client`** 消费 Canal 推送的变更消息。

### 3. 监听 Canal 实现缓存同步

```java
// 伪代码：用 canal-client 消费变更事件
CanalConnector connector = CanalConnectors.newSingleConnector(
        new InetSocketAddress("127.0.0.1", 11111), "example", "", "");

connector.connect();
connector.subscribe("tutorial.item");   // 订阅 item 表

while (running) {
    Message message = connector.getWithoutAck(100);   // 拉取变更
    long batchId = message.getId();
    for (Entry entry : message.getEntries()) {
        // 解析 RowData → 拿到主键 id
        // 删除 Redis: item:{id}、删除进程缓存、通知 Nginx 失效
        // 或直接更新各层缓存
    }
    connector.ack(batchId);   // 确认消费
}
```

**同步动作**：
- 数据库 **update/delete** → **删除**对应各层缓存（或更新）。
- 数据库 **insert** → 写入缓存。
- 相比"设置有效期"，Canal 能做到**近乎实时**的数据一致，同时不阻塞业务。

## 五、多级缓存整体架构回顾

```
                    ┌─────────────────────────────────────────────┐
浏览器 ──► Nginx/OpenResty ──► lua_shared_dict（Nginx 本地缓存）       │
                    │              │                               │
                    │              ▼（未命中）                     │
                    │           Redis（共享缓存）                   │
                    │              │                               │
                    │              ▼（未命中，HTTP 请求）          │
                    │        Tomcat 集群（按商品 id 哈希路由）       │
                    │              │                               │
                    │     ┌────────┴────────┐                     │
                    │  Caffeine 进程缓存    DB（MySQL）             │
                    └────────┤                                  │
                             └── 缓存回填：Caffeine ← Redis ← Nginx
                                                  ▲
                    DB 变更 ──► Canal ──► 缓存同步（删/更新各级缓存）
                                                    └──────────────┘
```

**分层缓存各施其职**：
- **Nginx 本地缓存**：最快，扛住绝大部分热点请求。
- **Redis**：共享、容量大，多实例间数据一致。
- **Caffeine 进程缓存**：Tomcat 内部，进一步减少 DB 与 Redis 压力。
- **Canal**：保证数据库与所有缓存层的数据同步，解决一致性问题。

## 六、核心要点速记

- **多级缓存**：浏览器 → Nginx 本地缓存 → Redis → JVM 进程缓存 → DB，逐级兜底、逐级回填。
- **Caffeine**：Java 高性能本地缓存，`maximumSize` + `expireAfterWrite`，`@Cacheable` 注解使用。
- **为什么比单级 Redis 快**：把热点数据放进程内存和 Nginx 内存，省去网络往返。
- **OpenResty（Nginx+Lua）**：`lua_shared_dict` 做本地缓存，`resty.http` 发请求给 Tomcat，`resty.redis` 查 Redis。
- **按商品 id 哈希负载均衡**：让同一商品固定打到同一台 Tomcat，才能命中 JVM 进程缓存。
- **缓存预热**：上线前把热点数据写入各级缓存，避免冷启动穿透 DB。
- **缓存同步**：设置有效期（简单但有窗口）→ 同步双写（耦合）→ **Canal 监 binlog（主流，解耦可靠）**。
- 多级缓存能扛超大并发，是**秒杀、抢购**等场景的关键架构。
