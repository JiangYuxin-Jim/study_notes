## 二、键值设计：如何设计优雅的 Key

### 1. 基本规范（命名约定）

**通用命名格式**（项目/业务 隔离 + 分层）：

```
{业务名}:{数据id}:{字段}
例：item:1001、user:9527:info、order:20260804:01
```

**质量要求**：
- **可读性**：key 语义清晰，别人一看就知道存的是什么。
- **简洁性**：不要过长，避免浪费内存（key 本身也占内存）。
- **唯一性**：加业务前缀，避免不同业务 key 冲突。
- **分层分目录**：用冒号 `:`（或 `::`）做层级分隔，便于用 `SCAN`/`KEYS` 按前缀管理。
- **统一小写**（约定俗成），避免大小写混乱。
- 避免使用无意义或过长的 key，如 `a1b2c3`、`this_is_a_very_long_key_for_no_reason`。

**反例 vs 正例**：

```text
❌ 反例：
  key = "1001"            ← 无业务语义，易与别的业务冲突
  key = "item-info-2026"  ← 语义不清、无层级

✅ 正例：
  key = "item:1001"                      ← 业务:id
  key = "user:9527:info"                 ← 用户信息
  key = "order:detail:20260804:01"       ← 订单详情
```

### 2. 配合 TTL（过期时间）

- 尽量给 key 设置合理的 **TTL**（过期时间），避免"永久 key"堆积撑爆内存。
- 热点/临时数据（验证码、会话、限流计数）设置短 TTL。
- 结合业务有效期设计过期策略，而不是放任 key 永不过期。

### 3. 用 SCAN 代替 KEYS

- `KEYS *` 会**阻塞 Redis**，生产禁止使用（单线程扫描全库）。
- 用 `SCAN cursor [MATCH pattern]` **增量迭代**，分批返回，不阻塞。

```text
SCAN 0 MATCH item:* COUNT 100
```

## 三、键值设计：BigKey 问题

### 1. 什么是 BigKey

**BigKey** 指**单个 key 的 value 过大**，常见三类：

| 类型 | 判定标准 | 危害 |
|------|---------|------|
| **String 类型 value 过大** | value 超过 **10KB**（严格点如 1MB 以上） | 网络传输慢、占用内存大 |
| **集合类型元素过多** | 如 Hash/List/Set/ZSet 元素超过 **1 万**（或体积超一定阈值） | 单次操作耗时、阻塞 |
| **集合类型某元素 value 过大** | 单个元素大到数 MB | 同上 |

**通用判定**：单个 key 的数据量超过 **10KB** 或集合**元素过多**（如 >10000），就要警惕。

### 2. BigKey 的危害

1. **网络阻塞**：BigKey 读写要传输大数据，占用带宽，拖慢其他命令。
2. **单线程阻塞**：Redis 是单线程，处理一个大 key 的操作（如 `HGETALL` 一个超大 hash）会**阻塞其他所有命令**，造成卡顿、超时。
3. **内存不均**：大 key 占用大量内存，集群中某节点内存使用率飙升，触发淘汰/迁移问题。
4. **删除/迁移困难**：`DEL`/`UNLINK`、数据迁移时大 key 耗时长，删大 key 也可能阻塞（老版本）。

### 3. 如何发现 / 检测 BigKey

- **`redis-cli --bigkeys`**：内置扫描命令，找出大 key 分布情况。
- **`MEMORY USAGE key`**：查看指定 key 的内存占用（字节）。
- **监控**：`info memory` 观察 `used_memory`、`used_memory_peak`，或对节点做内存分析。
- **DEBUG OBJECT / 业务埋点**：按需统计大 key。

```bash
# 扫描大 key（会遍历数据库，建议低峰期执行）
redis-cli --bigkeys

# 查看单个 key 内存占用
redis-cli MEMORY USAGE item:1001
```

### 4. BigKey 的处理方案

| 方案 | 说明 |
|------|------|
| **拆分** | 把大 key 按业务维度拆成多个小 key（如 hash 拆成多个、list 分段）。 |
| **压缩** | value 过大先压缩（如 JSON 压缩存储），减少体积。 |
| **不存储大对象** | 大文件/大对象存对象存储（OSS），Redis 只存**引用/ID**。 |
| **集合类控制元素** | 限制单 key 元素数量，必要时分批存取。 |
| **用惰性删除** | 大 key 用 `UNLINK key`（异步删除，不阻塞主线程）而不是阻塞的 `DEL`。 |
| **分批操作** | 大集合读写用 `HSCAN`/`SSCAN`/`LRANGE` 分页，避免一次全量。 |

> 一句话：**避免 BigKey**，是 Redis 高性能的第一原则。宁可多几个小 key，也不要一个超大 key。

## 四、键值设计：选择合适的数据结构

Redis 每种数据结构都有**适用场景**和**内存/性能特性**，选错会浪费内存或性能差。

| 数据结构 | 底层实现 | 典型场景 | 选择理由 |
|----------|----------|----------|----------|
| **String** | SDS（动态字符串） | 简单 KV、计数、缓存对象（JSON 序列化）、分布式锁、验证码 | 简单高效，可自增自减（INCR） |
| **Hash** | 哈希表 + ziplist/listpack | 对象存储、按字段存取（用户信息、商品详情多字段）| 可按 field 单独读写，省内存（field 紧凑）|
| **List** | 双向链表 / quicklist | 消息队列、最新列表（朋友圈）、时间线 | 头尾 O(1)，支持阻塞（BRPOP）|
| **Set** | 哈希表 / intset | 去重、共同好友（交集）、随机抽奖（SRANDMEMBER）| 去重 + 集合运算（交并差）|
| **ZSet** | 跳表 + 哈希表 | 排行榜、延迟队列、附近的人（按分数排序）| 按分数排序 + 范围查询，有序 |
| **Bitmap** | String 位操作 | 用户签到、在线状态、统计（UV 去重）| 极省内存（一位一事件）|
| **HyperLogLog** | 概率计数 | UV 统计、去重计数 | 12KB 固定内存做海量去重（有误差）|
| **GEO** | ZSet 封装 | 附近商铺、LBS | 地理距离计算、半径查询 |
| **Stream** | 消息队列专用 | 消息队列（可靠、消费者组）| 更完善的消息模型（比 List 队列强）|

**选择原则**：
1. **按访问模式选**：要按字段读写 → Hash；要排序/排名 → ZSet；要去重/交集 → Set；只要计数 → String/INCR。
2. **按内存效率选**：小对象用 `ziplist/listpack`（编码压缩）比 hash 表省内存；`intset` 比哈希省内存。
3. **能用更省内存的就不选重的**：如纯计数用 `INCR`（String）即可，不必用计数集合；去重计数用 **HyperLogLog**，精确去重要求才用 Set。
4. **大对象结合压缩 / 拆分**（呼应 BigKey 治理）。

## 五、核心要点速记

- **优雅 key**：`业务名:数据id:字段`，可读、简洁、唯一、分层、统一小写、配 TTL。
- **生产禁用 `KEYS *`**，用 `SCAN` 增量扫描。
- **BigKey 判定**：value > 10KB，或集合元素 > 1 万，就要治理。
- **BigKey 危害**：网络阻塞 + 单线程阻塞 + 内存不均 + 删除困难。
- **BigKey 检测**：`--bigkeys`、`MEMORY USAGE`。
- **BigKey 处理**：拆分、压缩、不存大对象、元素限流、`UNLINK` 异步删、分批操作。
- **数据结构选择**：按访问模式 + 内存效率权衡，能省内存就不选重的（intset/ziplist/HyperLogLog）。
