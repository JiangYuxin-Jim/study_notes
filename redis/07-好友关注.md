## 1. 业务场景概述

社交类应用的核心功能之一：用户可以**关注**其他博主，查看关注者的探店笔记动态。

```
用户A ──→ 关注 ──→ 用户B
                    ├── 发笔记1 → A在动态流中看到
                    ├── 发笔记2 → A在动态流中看到
                    └── ...
```

### 2.2 关注/取关接口

```java
@PutMapping("/{id}/{isFollow}")
```

### 2.3 共同关注 — Redis SortedSet 的应用

**需求**：查看自己和某个好友，**共同关注了哪些人**。

```
用户A关注了：[张三, 李四, 王五, 赵六]
用户B关注了：[张三, 王五, 钱七]

共同关注：   [张三, 王五]
```

#### 为什么用 Redis？

- 交集运算 `SINTER` 是 Redis Set 的强项
- 避免在 MySQL 中做 JOIN + 集合运算，性能差
- 每个用户关注的人不多，Set 内存占用可控

#### 数据结构设计

```redis
# 用户A的关注列表
SADD follow:1001 2001 2002 2003 2004
# 用户B的关注列表
SADD follow:1002 2001 2003 2005

# 求共同关注（交集）
SINTER follow:1001 follow:1002
# → ["2001", "2003"]
```

#### 缓存策略：关注时写入 + 查询时直接交

```java
// 关注时，同步写入 Redis
@PutMapping("/{id}/{isFollow}")
public Result follow(@PathVariable Long id, @PathVariable Boolean isFollow) {
    Long userId = UserHolder.getUser().getId();
    String key = "follow:" + userId;

    if (isFollow) {
        Follow follow = new Follow();
        follow.setUserId(userId);
        follow.setFollowUserId(id);
        save(follow);
        // 同步写入 Redis Set
        stringRedisTemplate.opsForSet().add(key, id.toString());
    } else {
        remove(query().eq("user_id", userId).eq("follow_user_id", id));
        // 从 Redis 移除
        stringRedisTemplate.opsForSet().remove(key, id.toString());
    }
    return Result.ok();
}

// 查询共同关注
@GetMapping("/common/{targetUserId}")
public Result followCommons(@PathVariable Long targetUserId) {
    Long userId = UserHolder.getUser().getId();
    String myKey = "follow:" + userId;
    String targetKey = "follow:" + targetUserId;

    // Redis Set 求交集
    Set<String> intersect = stringRedisTemplate.opsForSet()
        .intersect(myKey, targetKey);

    // 根据交集结果查用户信息
    List<UserDTO> userList = intersect.stream()
        .map(id -> userService.getById(Long.valueOf(id)))
        .map(UserUtil::toDTO)
        .collect(Collectors.toList());

    return Result.ok(userList);
}
```

## 3. 关注推送 — Feed 流

### 3.1 什么是 Feed 流？

Feed 流（信息流）是指，当你关注了某个博主后，该博主发布的**最新动态**会实时推送到你的信息流中。

```
你关注了 张三、李四、王五
         ↓
张三发了一篇探店笔记 → 你的 Feed 流中出现这篇笔记
李四发了一篇探店笔记 → 你的 Feed 流中出现这篇笔记
         ↓
你打开 App → 看到「最新动态」→ 按时间倒序展示
```

### 3.2 Feed 流的三种推送模式

| 模式 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| **推模式（Fanout）** | 博主发笔记 → 推送给所有粉丝 | 粉丝查看时无需聚合，直接读自己的收件箱，延迟低 | 大V粉丝多时，写放大严重 |
| **拉模式（Pull）** | 粉丝刷新时 → 拉取所有关注者的笔记 | 写操作轻，只有一份数据 | 粉丝查看时需聚合大量数据，延迟高 |
| **推拉结合（混合模式）** | 普通粉丝推，大V粉丝拉 | 取长补短 | 实现复杂 |

### 3.3 本项目的选择：推模式

本项目采用**推模式**（适合中小规模场景），为每个用户维护一个**收件箱（Inbox）**。

```
博主发笔记 ──→ 遍历博主的所有粉丝
                   ↓
             向每个粉丝的收件箱（SortedSet）中插入笔记ID
                   ↓
粉丝刷新动态 ──→ 从自己的收件箱 SortedSet 中拉取
```

### 3.4 数据结构选择：SortedSet

```
Key:   feed:userId               （每个用户有自己的收件箱）
Type:  ZSET (Sorted Set)
Score: 笔记发布时间戳（毫秒级）
Value: 笔记ID
```

**为什么用 SortedSet 不用 List？**
- SortedSet 支持按 score 分页查询（`ZREVRANGEBYSCORE`）
- List 只能按 index 翻页，如果期间有新数据插入，翻页会偏移
- SortedSet 的 score 天然支持**滚动分页**（以最后一篇笔记的时间戳为游标）

### 3.5 推送实现（发笔记时）

```java
// 博主发笔记时，推送给所有粉丝
@PostMapping("/blog")
public Result saveBlog(@RequestBody Blog blog) {
    Long userId = UserHolder.getUser().getId();
    blog.setUserId(userId);
    blogService.save(blog);

    // 查所有粉丝
    List<Follow> fans = followService.query()
        .eq("follow_user_id", userId)
        .list();

    // 推送给每个粉丝
    for (Follow fan : fans) {
        Long fanId = fan.getUserId();
        String key = "feed:" + fanId;
        // 笔记ID为value，时间戳为score
        stringRedisTemplate.opsForZSet()
            .add(key, blog.getId().toString(), System.currentTimeMillis());
    }

    return Result.ok(blog.getId());
}
```

### 3.6 滚动分页查询

```java
@GetMapping("/blog/of/follow")
public Result queryBlogOfFollow(
        @RequestParam("lastId") Long lastId,      // 上一次查询的最后时间戳
        @RequestParam(value = "offset", defaultValue = "0") Integer offset  // 偏移量
) {
    Long userId = UserHolder.getUser().getId();
    String key = "feed:" + userId;

    // ZREVRANGEBYSCORE key max min LIMIT offset count
    // 查询 score < lastId 的前3条（滚动分页）
    Set<ZSetOperations.TypedTuple<String>> typedTuples = stringRedisTemplate
        .opsForZSet()
        .reverseRangeByScoreWithScores(key, 0, lastId - 1, offset, 3);

    if (typedTuples == null || typedTuples.isEmpty()) {
        return Result.ok(Collections.emptyList());
    }

    // 解析结果
    List<Long> ids = new ArrayList<>(typedTuples.size());
    long minTime = 0;
    int os = 1;  // 下次查询的偏移量
    for (ZSetOperations.TypedTuple<String> tuple : typedTuples) {
        ids.add(Long.valueOf(tuple.getValue()));
        long time = tuple.getScore().longValue();
        if (time == minTime) {
            os++;  // 同一时间戳出现多次 → 偏移量递增
        } else {
            minTime = time;
            os = 1;
        }
    }

    // 查笔记详情（按ID）
    String idStr = StrUtil.join(",", ids);
    List<Blog> blogs = blogService.query()
        .in("id", ids)
        .last("ORDER BY FIELD(id," + idStr + ")")  // 保持顺序
        .list();

    return Result.ok(blogs);
}
```

**滚动分页 vs 传统分页：**

```
传统分页（page/size）：
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │ 7  │ 8  │
└────┴────┴────┴────┴────┴────┴────┴────┘
page=1,size=3 → [1,2,3]
          ↓ 新笔记9插入到1前面 ↓
┌────┬────┬────┬────┬────┬────┬────┬────┬────┐
│ 9  │ 1  │ 2  │ 3  │ 4  │ 5  │ 6  │ 7  │ 8  │
└────┴────┴────┴────┴────┴────┴────┴────┴────┘
page=2,size=3 → [4,5,6]（跳过了9！）

滚动分页（lastId/offset）：
以最后一篇笔记的时间戳为游标，每次从该时间戳之前取
新数据插入不影响游标位置，不会出现"跳过"或"重复"
```

## 4. 关键知识点总结

| 技术 | 用途 | 数据结构 |
|------|------|---------|
| Set | 关注列表、共同关注（交集） | `follow:{userId}` |
| SortedSet | Feed流收件箱（时间排序） | `feed:{userId}` |
| ZREVRANGEBYSCORE | 滚动分页查询 | 按score倒序取 |
| 推模式 | 笔记推送至粉丝收件箱 | 写放大（每个粉丝写一次） |

## 思考

- **大V场景**：推模式遇到千万粉丝大V，一次发笔记要写千万次。实际方案通常是推拉结合：普通粉丝走推模式，大V粉丝走拉模式（发笔记时只塞进"大V粉丝专用收件箱"）
- **Feed流淘汰**：SortedSet 的 feed 如果只进不出，数据量会无限增长。需要做清理：只保留最近30天或最近500条。
- **时间戳重复问题**：如果同一毫秒内有多条笔记，会导致滚动分页的 `lastId` 重复。解决方案就是上面的 `offset` 递增策略。
